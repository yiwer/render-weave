# 05: 审核数据定义候选并发布为静态数据定义

**What to build:** 代建工程师在本地审核页对照示例图审核数据定义候选，逐项处理待确认项；审核通过后，用 `renderweave agent apply` 发布为静态数据定义。

**Blocked by:** 04

**Status:** resolved

**Trace:** 第三阶段 PRD；用户故事 7–9、11–13；验收 A07、A08。

- [x] 审核页由本地命令打开，包括：
  - 示例图，可局部放大；
  - 字段清单：名称、类型、约束、对应图上哪一部分；
  - 编译产物摘要；
  - 待确认项与 Agent 的说明。
- [x] 待确认项逐项处理：采纳候选、改值或标为空；其余值整体确认一次（M47）。审核结果保存为 `review.json`，可以关闭后重开继续。
- [x] `apply` 只接受审核通过的轮次，经发布入口发布为下一个版本（M18）；审核时改过的内容以审核结果为准。
- [x] 以下情况拒绝应用，列出差异，并要求明确选择覆盖或重做（M51）：
  - 工作区中的同名数据定义已发布了新版本；
  - 工作区指纹已变化。
- [x] 未审核、审核未通过以及应用失败时，工作区保持不变。

**测试接缝：** 公开 CLI 与审核结果文件。审核页以接口级测试为主，另在浏览器里手动走查一遍，并截图存档。

## Answer

2026-10-15 已完成。

**成果**

- **命令**：
  - `renderweave agent review <轮次目录>`：在 `127.0.0.1` 上启动审核页；
  - `renderweave agent apply <轮次目录> [--workspace] [--overwrite]`：应用审核通过的轮次。

  说明见 [docs/agent-tasks.md](../../../docs/agent-tasks.md#审核)，决定见 M227。
- **实现**：
  - `src/agent/review.ts`：公开入口 `readReview`、`changeReview`、`applyAgentRound`；
  - `src/agent/review-server.ts`：审核页服务，只用 `node:http`；
  - `web/review.html`：页面，Agent 写的内容一律按纯文本显示；
  - `src/schema/publish-files.ts`：从 `publish` 命令挪出的文件命名与排他写入，两条命令共用。
- **审核页**：
  - 示例图可适应窗口、按档位或单击放大，"定位"跳到字段区域并框出；
  - 字段清单：名称、类型、约束、图上位置、说明与相关待确认项；
  - 编译产物摘要：将发布的版本、属性数、必填字段与完整 JSON Schema；
  - 待确认项卡片，以及 Agent 的说明与用量。
- **字段的图上位置**：原成果格式没有这项信息，Agent 的成果因此增加可选的 `locations`（文字描述，可带像素区域），资料与成果格式文档同步修改。这是 Agent 的自述，不是识别证据（M220）。
- **待确认项的处理**（数据定义中）：
  - 采纳候选：保留候选文件中的写法；
  - 改值：替换整个字段，没有位置时替换整份定义；
  - 标为空：删去该字段，没有位置时不发布这份候选。

  待确认项全部处理、其余内容整体确认、引擎校验没有严重问题，三者都满足才能通过。
- **review.json**：用 `outcomeSha256` 绑定所审核的成果；每次操作整份替换，关闭后重开可以继续；给出结论后要先撤回才能再改，应用后不能再改。
- **应用**：
  - 应用前重新核对审核结果与候选哈希；
  - 工作区指纹变化时，列出同名定义的新版本与新增、删除、修改的文件，然后拒绝；
  - 加 `--overwrite` 即选择覆盖，按当前工作区发布为下一个版本，候选之间的引用改到新版本；重做就是基于当前工作区重新发起一轮；
  - 全部定义先在内存中发布成功，再排他写入，失败时撤回已写文件；
  - 成功后写 `applied.json`，同一轮不能再应用。
- **问题码**：`round.invalid`、`review.pending`、`review.invalid`、`review.notApproved`、`apply.workspaceChanged`、`apply.alreadyApplied`、`apply.failed`。

**不依赖模型的测试**（`test/agent-review.test.ts` 12 项；`test/agent.test.ts` 新增 4 项）

- **审核视图**：
  - 字段的类型与约束文字、图上位置、相关待确认项、编译产物摘要；
  - 版本接在快照之后（问候 v2）；
  - 未处理时不能通过，且不写 `review.json`。
- **审核操作**：
  - 改值、标为空、采纳后可以通过，重新读取后处理结果仍在；
  - 给出结论后要先撤回才能修改；
  - 9 种不合规操作各有用例；
  - 改值后定义不合格时不能通过；
  - 同一位置的处理结果不一致时报出；
  - 整份标为空后，引用它的定义报 `definition.refNotFound`；
  - 整份改值按字段比对，标出保留、改过、已删去；
  - 审核结果与成果对不上、候选被改动、目录不是轮次时都不能继续。
- **应用**：
  - 未审核、审核中、未通过时拒绝，工作区一字不变；
  - 通过后发布为新版本，改过的字段以审核结果为准；
  - 不能再次应用，应用后不能再改审核结果；
  - 工作区变化时给出差异（新增文件、修改文件、同名定义的新版本）并拒绝，工作区一字不变；
  - 覆盖后场次发布为 v2，胸牌对场次的引用改到 v2；
  - 写到第三份定义时排他创建失败，前两份撤回，工作区一字不变。
- **命令行与服务**：
  - `apply` 的 4 种用法错误退出码为 2；未审核、工作区已变化时为 1；`--overwrite` 后为 0；本轮没有工作区时要求 `--workspace`；
  - `review` 打印地址；页面、示例图与审核结果的读写都可用；
  - 跨站 `Origin` 返回 403，非 JSON 请求返回 415，非本机 `Host` 返回 403；
  - 取消信号到来后退出码为 0，端口随之释放。
- **成果格式**：图上位置的 3 种结构问题；`agent/reference/outcome.md` 中的示例本身结构合格。
- **能否变红已验证**：临时让以下四处失效，相应用例都失败，之后已恢复：
  - 工作区指纹比对；
  - 写入失败后的撤回；
  - `Host` 核对；
  - 通过条件。

**偏差与说明**

- 成果格式增加 `locations`，是对票据 04 合同的加法：旧轮次没有它，照样能审核。
- 只有待确认项能逐项改；审核中发现其他字段有误，就判不通过、带反馈重跑（票据 07）。如果实际审核中常要改其他字段，再开放任意字段改值（M227）。
- 编码规范的引擎边界补了一句：命令行附带的本地页面不算 HTTP 服务外壳。
