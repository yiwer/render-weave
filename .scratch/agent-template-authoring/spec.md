# 第三阶段 PRD：Agent 代建模板的本地闭环（v0.3）

2026-10-14。第二阶段完成了本地出图与可复现交付。M209–M217 验证了业务 Agent 的运行方式：Claude Code 加 qwen3.8-max 能看示例图、调用渲染工具；交给它通用指南、领域约定与项目说明三层资料时，数据定义与模板基本不用返工。本期把验证脚本中证明可行的部分做成内部团队可用的代建工具，对应路线图的阶段 3 与稳定版本 v0.3（M207）。

## Problem Statement

验证结论目前只存在于一次性的验证脚本 `scripts/m190/` 中，离日常代建还缺四件事：

- **DSL 没有成文契约。** 写法散落在 M402 样例 README 的 S1–S31 约定与解析器里。Agent 用的语法参考是验证时临时整理的，没有 JSON Schema，也没有兼容承诺。v1.0 的开放 API 与表单生成（M206）都要建立在稳定写法上。
- **工具服务是一次性实现。** MCP 服务放在验证脚本里，工具合同随手可改，没有合同测试。只读与路径限制的保证也只靠脚本自觉。
- **任务没有闭环。** Agent 交回的是一堆候选文件：没有 `outcome.json` 合同（M48），没有待确认项结构（M44），没有审核界面（M47），也没有"应用"路径。代建工程师要手工复制候选、自己发布、自己对照预览，返工信息无处沉淀。
- **质量没有门槛。** ADR-0015 把"升级 Claude Code 或换模型后复跑验证"列为代价，但复跑结果没有通过线，资料与评估场景也还在验证目录里。

## Solution

把验证中已证明可行的部分产品化，并用评估场景守住质量：

1. **DSL 1.0**：冻结数据定义、模板、数据集、渲染请求与批次请求的现行写法。给出人读参考、Agent 参考与 JSON Schema，与解析器做一致性测试，并写下兼容策略。
2. **MCP 工具服务**：工具服务进入引擎仓库，提供 `renderweave mcp`。工具全部只读：读取、校验、草稿预览、元素检查、局部放大、资源列表、DSL 参考。工具合同就是 v0.3 承诺的稳定接口。
3. **任务闭环**：用 `renderweave agent` 按 M43 的四种任务发起一轮（ADR-0015 的运行方式），交回 `outcome.json`。RenderWeave 先校验结构，再重新渲染预览（M52）。代建工程师在本地审核页逐项处理待确认项（M47），审核通过后由 `apply` 写入工作区：数据定义经发布入口发布，数据集与模板保存。审核时可以带反馈再来一轮（M58）。
4. **资料与评估**：三层资料成为仓库内的正式文件，评估场景（M402、366）成为升级的回归门槛。

### 完成标准

一位内部代建工程师按中文指南，用一张新示例图走完以下流程：

数据定义提取 → 审核、发布 → 数据集提取 → 审核、应用 → 模板辅助设计 → 审核、应用 → 正式出图 → 一轮模板修改。

全程只用 `renderweave` 命令与审核页，不手工复制文件。同时记录人工时间、返工点与待确认项数量。此外，评估场景连续两次达到通过线，现有测试与样例没有回归。

## User Stories

代建工程师（内部模板作者）：

1. 作为代建工程师，我想用一条命令对示例图发起数据定义提取，以便不必自己拼 Claude Code 的参数、环境与工具配置。
2. 作为代建工程师，我想用一份项目说明写明尺寸、目标范围、命名和客户说明，以便 Agent 按这一单的事实工作。
3. 作为代建工程师，我想为任务选一个领域约定包，以便 Agent 遵守行业约定；没有约定包时，它把领域缺口列为待确认。
4. 作为代建工程师，我想让任务在独占的工作目录与空白环境中运行，key 只经环境变量传入，以便不泄露凭据、不碰我的工作区。
5. 作为代建工程师，我想每轮都得到结构化成果（候选文件、待确认项、说明与用量），以便逐项审核。
6. 作为代建工程师，我想在成果结构不合格时拿到问题清单，自己决定是否带着问题重跑，以便不被自动重试消耗额度。

8. 作为代建工程师，我想在审核页把示例图与预览并排对照，并能局部放大，以便发现版面差异。
9. 作为代建工程师，我想逐项处理待确认项（采纳候选、改值或留空），其余值整体确认一次，以便审核工作量可控。

16. 作为代建工程师，我想在只有图片时被引导先做数据定义提取并发布，再做数据集提取，以便任务顺序符合 M43。
17. 作为代建工程师，我想看到每轮的用时、轮数与 token 用量，以便估计代建成本。
18. 作为代建工程师，我想更换模型或端点（缺省为千问 token plan 的 qwen3.8-max），以便在模型间切换（ADR-0003）。

## Implementation Decisions

M43–M53、M58、ADR-0001、ADR-0003、ADR-0015 继续有效。没有实施的能力不得写入"当前支持"清单。

### DSL 1.0

1. **DSL 1.0 的范围就是现行写法**：`renderweave-schema/1`、`renderweave-template/1`、数据集文档、渲染请求与 `renderweave-batch/1`，不改名、不改语义。冻结的含义是写下完整契约并承诺兼容，不是重新设计。已知能力边界照实写为限制，例如循环只能横向、没有段落换行、没有文本表达式。
2. **兼容策略**：
   - 1.x 内只做加法：新增可选键、元素类型或枚举值，旧文档的解析与出图结果保持不变。
   - 删除、改名或改语义要升到 `/2`，并给出迁移说明。
   - 解析器继续拒绝未知键，防止静默忽略。因此带新键的文档在旧引擎上会被拒绝，而不会被误渲染，这是有意为之。
   - 这项取舍写成 ADR。
3. **JSON Schema 与一致性**：五种文档各有一份 JSON Schema 2020-12，随仓库发布。一致性测试要求：
   - 仓库内全部有效语料（共享样例、夹具、测试工作区、指南示例）都通过 Schema；
   - 结构错误的变异样本（未知键、错类型、错枚举、缺必填）被 Schema 与解析器同时拒绝；
   - Schema 通过而引擎拒绝的情形，只限于列明的语义检查类别，例如引用是否存在、变量路径、绑定类型、调用基准。
4. **参考文档同源**：人读参考与 Agent 参考来自同一份契约。Agent 参考由 `scripts/m190/template-reference.md`、`dsl-reference.md` 演进而来，示例保持在非线路牌领域，避免向 Agent 泄露答案。两份参考中的示例都在测试中实际校验并渲染，0 问题才算通过。

### MCP 工具服务

5. **服务与工具**：工具服务进入引擎仓库，公开入口为 `renderweave mcp`（stdio）。工具如下：
   - 读取：工作区文档列表与内容、资源列表；
   - 校验：数据定义、数据集、模板静态检查；
   - 草稿预览：可用工作副本替代已保存模板（M50），可用内联数据集，返回图片与问题清单；
   - 元素检查：按元素路径返回布局摘要；
   - 局部放大：返回裁切放大后的图片；
   - DSL 参考与 JSON Schema。

   工具全部只读（M53），文件访问限于本轮工作目录与只读的工作区快照。
6. **工具合同就是 v0.3 的稳定接口**：合同包括名称、输入 Schema 与输出结构，由快照测试守护。新增工具或可选参数属于兼容改动；改名或删参数要升合同版本，并复跑评估。
7. **本期不做识别工具（OCR）**（M55、M56 的模型选择仍待实测）。因此待确认项不带来源证据，M45 的来源证据随识别工具落实。审核页对待确认项显示 Agent 的说明，并提供示例图局部放大供人核对。
   - **切换条件**：试用或评估中，如果"候选值无法核实"成为主要返工来源，就提前做识别工具。

### 任务闭环

8. **发起任务**：`renderweave agent run --task <任务类型> --sample <示例图> --brief <项目说明> [--domain <领域>] [--workspace <工作区>] [--from <上一轮>] [--feedback <反馈文件>]`。
   - 按 ADR-0015 启动一轮：受限模式，空白环境，独立配置目录，只连本仓库的 MCP 服务。
   - 本轮有独占目录，三层资料与 DSL 参考按任务类型组装。
   - key 只经环境变量传入；模型与端点经配置给出，缺省为千问 token plan 的 qwen3.8-max。
   - 进程环境不继承宿主的 `CLAUDE_*` 与 `ANTHROPIC_*` 变量。
9. **成果合同 `outcome.json`**（M48），内容包括：
   - 任务类型与轮次；
   - 基于的输入：示例图哈希、工作区快照指纹、上一轮引用；
   - 候选文件清单（数据定义、数据集、模板或工作副本）；
   - 待确认项：位置、候选值（可空）、原因，原因取 M44 的四类；
   - 说明，以及用量（用时、轮数、token）。

   RenderWeave 先校验结构，再用引擎校验候选。不合格时给出问题清单，由人决定是否带着问题清单重跑；不自动重试。
10. **审核**：审核页由本地命令打开。页面包括：
    - 示例图与 RenderWeave 重新渲染的预览并排（M52），两者都可局部放大；
    - 字段或模板清单；
    - 待确认项逐项处理：采纳候选、改值或标为空；其余值整体确认一次（M47）。

    数据集候选在待确认项全部处理之前不能生成（M46）。审核结果保存为 `review.json`，可以关闭后再打开继续。页面形态（本地服务还是生成的静态页）交给实施，外部行为以本条为准。
11. **应用**：`renderweave agent apply <轮次目录>` 只接受审核通过的轮次。
    - 数据定义经现有发布入口发布为静态数据定义（M18），数据集与模板写入工作区。
    - 应用前比对成果所基于的工作区指纹；已变化则列出差异，要求明确选择覆盖或重做（M51）。
    - 应用失败时，工作区保持原状。
12. **多轮**（M58）：下一轮的输入是素材、上一轮成果（含审核时的修改）与反馈文本。每轮一个独立目录，轮与轮之间的状态由 RenderWeave 保存。
13. **模板辅助修改**：输入是已保存的模板与修改要求，要求可以带元素路径。成果是工作副本（M49）与结构化差异；审核页显示修改前后的预览，两者都由 RenderWeave 渲染（M50、M52）。
14. **任务顺序**（M43）：
    - 数据集提取要求所选数据定义已经发布；
    - 模板辅助设计要求数据定义已发布、数据集已保存；
    - 只给图片时，命令提示先做数据定义提取。

### 资料与评估

15. **资料归档**：三层资料迁入 `agent/`：`guide.md`、`domains/<领域>.md`、`briefs/` 下的项目说明模板。归属规则沿用 M216：与行业无关的写进通用指南，只在某个行业成立的写进领域约定，只关于这一单的写进项目说明。
16. **评估工具**：`scripts/m190/` 迁为评估工具，走产品路径，也就是用 `renderweave agent` 与 MCP 服务发起任务。评估需要 key、耗时长、消耗额度，所以不进 `npm test`；在升级 Claude Code、换模型、改资料或改工具之后手动运行，报告存档。
17. **通过线**（以 M213–M217 实测为基线；单次运行波动较大，所以要求连续两次都达线，这一点是推断）：
    - M402 数据定义：6 项约定全部通过，专家字段至少 14/15；
    - M402 模板：10 个压测场景全部通过，两项版面检查（M215）通过；
    - 366 数据定义：站名至少 57/59，地标至少 14/15，设施图标至少 17/18。

## Testing Decisions

### 接缝与既有实践

- **DSL**：用一致性测试对齐 Schema 与解析器，语料来自仓库现有文档，另加变异样本；不为解析器内部函数单独写测试。
- **MCP 服务**：用 JSON-RPC 客户端（不经模型）测合同，内容包括：
  - 工具清单与输入 Schema 的快照；
  - 每个工具的正常与异常输入；
  - 只读与路径限制；
  - 图片内容返回；
  - 工作副本预览不改动已保存模板。
- **任务闭环**：结构校验、审核结果、应用（发布、写入、冲突、拒绝未审核）都通过公开入口与 CLI 测试。测试中用构造好的 `outcome.json` 与候选文件代替模型输出，不依赖 key。
- **模型相关行为**：只由评估门槛衡量，不在单元测试中断言模型输出。
- 好的测试给业务输入，断言能否发布、写入了什么、哪里被拒绝、已有内容是否保持；不断言私有模块与调用次数。

阶段收尾仍要执行全量测试、类型检查、构建、两轴代码审查，并产出第三阶段验收文档。

## Out of Scope

- **服务化（阶段 4）**：HTTP 服务、多租户、鉴权、数据库与对象存储、云上每轮容器、凭据按轮签发（M54）、并发与额度控制。
- **识别**：识别工具（OCR）、识别结果实体与来源证据（M45、M55、M56）。
- **交互界面**：原型 D 的对话加画布、评论定位与实时旋钮（M208），以及客户自助入口。
- **无人审核**：自动重试、自动应用、无人审核的批量代建。
- **DSL 新能力**：动态模板、纵向循环、段落换行、文本表达式等。DSL 1.0 只冻结现行写法。
- **其他**：Linux 上的 Agent 运行实测；token plan 的实际计费核对。

### 实施顺序

1. DSL 1.0：先做数据定义与数据集，再做模板与请求，同时完成参考、Schema 与一致性测试。
2. MCP 只读工具服务与合同测试。
3. 数据定义提取一轮：启动、`outcome.json`、结构校验与重新渲染。
4. 审核与应用：先打通数据定义的审核、发布，再扩展到数据集与模板。
5. 多轮反馈与模板辅助修改。
6. 资料归档与评估门槛。
7. 全阶段验收：端到端代建、跨平台、指南与两轴审查。

以上是依赖顺序，票据见本目录的 [README](README.md)。接口内部组织交给实施，外部行为与验收条件以本文为准。2026-10-14 用户确认拆分与上述决定，规划决定登记为 M218–M222。
