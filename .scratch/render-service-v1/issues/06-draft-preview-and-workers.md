# 06: 经渲染 worker 进程同步出草稿预览，超时与内存超限的渲染被结束，worker 自动恢复

**What to build:** 任务队列、worker 的调度进程与渲染子进程、模板列表与只读查看接口、同步草稿预览接口，以及入队前的限制检查。

**Blocked by:** 05

**Status:** resolved

**Trace:** [阶段 4 PRD](../spec.md)「服务结构」「开放 API」；用户故事 2、3、11、38、45、46；验收 A06、A07；ADR-0017。

- [x] 任务队列放在 PostgreSQL 里，worker 用 `SELECT … FOR UPDATE SKIP LOCKED` 领取任务。
- [x] 每个 worker 容器有一个调度进程和一个渲染子进程，一次只做一项。子进程在任务之间复用；超时、崩溃或做满一定项数后换新。
- [x] 模板列表与只读查看接口，返回名称、当前修订、适用尺寸范围、对外参数和所用的数据定义。
- [x] 草稿预览接口同步返回图片、问题清单与布局摘要，不计额度，按租户限制并发与频率。代建工程师可以用被指定租户的身份预览。
- [x] 执行隔离：
  - **单项超时**：调度进程结束子进程，本项失败，问题说明写明是超时；
  - **内存超限**：容器限制结束子进程，结果同上；
  - 两种情况下 worker 都自动恢复，后续任务照常完成。
- [x] 入队前在接口进程里检查限制，不出图，超限直接拒绝、不占 worker：
  - 请求与数据集的字节数；
  - 单张最大像素：取套餐值，且不超过引擎上限；
  - 循环展开后的项数与元素数。
- [x] 超时与内存上限可以配置；Docker 后端测试用极小的值，稳定触发上面两种情况。
- [x] 决定记 M 编号。

**测试接缝：** 开放 API。内存后端用进程内 worker；超时、内存超限与恢复只在 Docker 后端测。

## Answer

2026-10-19 完成。决定见 M266（任务队列与渲染 worker）与 M267（草稿预览与入队前的限制），说明见[出图服务](../../../docs/service.md#模板与草稿预览)与[渲染 worker](../../../docs/service.md#渲染-worker)。

**成果**

- **引擎**（公开入口新增三个，都不改已有行为）：
  - `measureRender`：与 `render` 共用展开段，量出像素、展开后会显示的元素数与循环项数，不加载 CanvasKit；无法展开时问题清单与 `render` 完全相同；
  - `describeTemplate`：模板的名称、基准、适用尺寸范围与对外参数；
  - `preloadRenderer`：渲染子进程启动时预先加载 CanvasKit。
- **任务队列**：迁移 0004 加 `render_tasks` 表（开行级安全）与属主身份执行的领取函数 `rw_claim_task`（`FOR UPDATE SKIP LOCKED`）；内存后端有同样语义的队列。
- **worker**（`service/src/worker/`）：
  - 调度进程领取任务，交给渲染子进程；
  - 子进程自己连库与对象存储，启动时调高 `oom_score_adj`、预加载 CanvasKit；
  - 单项超时由调度进程结束子进程；内存超限由容器限制结束子进程，凭 cgroup `memory.events` 认出；
  - 做满项数、超时、内存超限或崩溃后换新并预热；
  - 健康检查带渲染器的计数。

  Compose 给 worker 设内存上限并关掉交换分区，单项超时与换新项数可经环境变量配置。
- **端点**：
  - `GET /v1/templates`、`GET /v1/templates/{模板名}`；
  - `POST /v1/previews`，代建工程师用 `POST /v1/authoring/tenants/{租户}/previews`；
  - 预览同步返回图片（base64）、问题清单与布局摘要。
- **入队前的限制**：请求与已保存数据集的字节数、单张像素、展开后的元素数与循环项数，超限答 413；按租户限预览的并发与频率，超过答 429；等不到 worker 答 503 并撤回。
- **精度**：全部 JSON 请求体按原文检查，超过 15 位有效数字答 400（M112）。
- **文档**：`docs/service.md` 加"模板与草稿预览""渲染 worker"两节，配置、端点、问题码与测试同步；代建指南第 9 步加推送后自查；`GLOSSARY.md` 加渲染 worker；M266、M267。

**判断**

- **worker 没渲染完时预览仍答 200**：没有图片，问题清单写 `worker.timeout`、`worker.memoryExceeded` 等，与引擎"无法出图时只有问题清单"一致；HTTP 错误留给请求本身的问题。
- **无法展开的请求不入队**：接口进程已经算出与单次渲染相同的问题清单，不再占 worker。
- **单张像素上限**：套餐要到票据 09 才有，先取引擎上限 1 亿。
- **撤回的任务算频率、不算并发**；入队超过等待时长的任务也不算并发，worker 中途退出时租户不会一直被卡住。
- **关掉交换分区**：不关时超限只会变慢，最后报成超时，分不出内存问题。
- **数值都是暂定的**：单项超时 30 秒、500 项换新、内存 2 GB、元素 20,000、循环项 2,000、预览并发 2、每分钟 60 次，由容量基线（票据 15）实测后定。

**没做**：任务行的定期清理（结果取走后已清掉图片与布局，行本身还在）、队列积压的指标。都留给票据 15。

**实测**（Windows，Node v24，临时度量脚本，没进仓库）：

- 问候牌草稿每像素约 13 字节：1 亿像素峰值约 1.3 GB、3 秒；只有一种字体的小图峰值约 210 MB。
- 纵向循环 6,000 项文字约 4 秒、峰值约 400 MB。
- 像素同时拉高用时和内存，所以超时用"费时不费内存"的长循环触发，内存超限用 1 亿像素触发。

**验证**

- **引擎**（`test/render-measure.test.ts`，9 项）：
  - 问候牌与 M402 的像素、元素数与循环项数，与实际渲染的图片和布局摘要逐项一致；
  - 四种无法展开的请求，问题清单与 `render` 完全相同；
  - 模板说明只列对外参数，读不了的模板只有问题清单。
- **内存后端**（`service/test/preview.test.ts`，8 项，进程内 worker）：
  - 模板列表与查看；
  - 预览的图片、问题清单与布局摘要与本机直接渲染逐字节、逐项相同，写 `final` 答 400；
  - 无法展开的请求直接答问题清单；
  - 五种限制各答 413，元素与循环项同时超限时两条都报，过精的数值答 400；
  - 并发、频率与等不到 worker：两个排队等不到答 503、第三个超过并发答 429，撤回的任务不再渲染，一分钟后恢复；
  - worker 卡住时答 503，等待时长过后不再占并发；
  - 代建预览、审计与别的租户 404；日志里没有密钥。
- **权限矩阵与跨租户端点清单**：新加 4 个端点，矩阵 28 个端点、清单 18 个端点逐项通过。
- **Docker 后端**：`node service/scripts/test-docker.mjs` 从空环境起服务，7 个文件、57 项通过，服务日志 40 行都是合格的 JSON。其中预览 10 项由 Compose 里真实的 worker 渲染；脚本给 worker 设单项超时 1.5 秒、内存 512 MB、5 项换新：
  - 6,000 项的循环答 `worker.timeout`，超时计数加 1，之后的预览与本机逐字节相同；
  - 1 亿像素的草稿答 `worker.memoryExceeded`，内存超限计数加 1，之后照常；
  - 连做 10 项，子进程换新 1–2 次；
  - 行级安全把 `render_tasks` 加进覆盖范围，15 张带 `tenant_id` 的表都通过。

  第一次跑时频率用例失败：这个用例给真实 worker 也只等 300 ms，worker 轮询加读字体来不及就答了 503。是用例的问题，改为真实 worker 等 10 秒后通过。
- **变异检查**：
  - **内存后端 13 处**：不查像素、循环项、已保存数据集字节数，不限并发，撤回的任务不算频率，卡住的任务一直占并发，等不到时不撤回，预览接受正式模式，JSON 不查精度，代建预览不查租户，模板列表带内部参数，度量不数循环项，预览不记审计。全部被抓住，无害的对照改动全过。
  - 起初"等不到时不撤回"没抓到：等待时长规则让撤回与否看不出来。补了"新起的 worker 只做了这一项"的断言后抓到。
  - **Docker 后端 3 处**：超时不结束子进程、不认内存超限、做满项数不换新，每处各跑一遍 Docker 后端测试，都让对应用例失败。
