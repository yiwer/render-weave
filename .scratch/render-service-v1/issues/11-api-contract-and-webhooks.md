# 11: 开放 API 有可快照的 OpenAPI 合同，批次结束时发带签名的 webhook

**What to build:** OpenAPI 描述与快照测试、统一的错误与状态码映射、webhook 的注册、签名、重试与投递记录，以及 API 兼容策略文档。

**Blocked by:** 08、09、10

**Status:** resolved

**Trace:** [阶段 4 PRD](../spec.md)「开放 API」；用户故事 25、26、28、29、31；验收 A06、A10；M246。

- [x] 全部端点都有 OpenAPI 描述，并做快照测试。快照有变化时必须显式更新，并在文档里写明是否兼容。
- [x] 错误一律带问题清单（问题码、等级、位置、说明）。HTTP 状态按类别映射，逐个端点核对：
  - 400 请求不合法；401 未鉴权；403 无权限；
  - 404 不存在；409 冲突；429 额度不足或限频。
- [x] webhook：
  - 客户管理员和 API 密钥能注册、停用 webhook；
  - 批次结束时（完成、部分失败、取消）投递一次，正文带批次摘要；
  - 用租户的签名密钥对正文做 HMAC 签名，附带时间戳；
  - 投递失败按指数退避重试有限次，投递记录可查。
- [x] 文档：写开放 API 的使用说明，以及 1.x 兼容策略：只做加法，比照 ADR-0016。
- [x] 决定记 M 编号。

**测试接缝：** 开放 API。webhook 用测试里自建的接收端，验证签名与重试。

## Answer

2026-10-20 完成。决定见 M276（OpenAPI 合同、错误映射与 1.x 兼容策略）与 M277（webhook）。客户开发者的使用说明见[开放 API](../../../docs/api.md)，维护说明见[出图服务](../../../docs/service.md#开放-api-描述)的“开放 API 描述”与“webhook”两节。

**成果**

- **OpenAPI 描述**：`GET /v1/openapi.json` 公开返回 OpenAPI 3.1，覆盖全部 65 个端点（含 `/healthz`、`/readyz` 与它自己），另在 `webhooks` 里描述 `batch.finished` 事件。
  - 路径、方法与请求的 JSON Schema 取自已注册的路由，也就是服务实际执行的校验；说明、回答与错误状态写在 `service/src/api/openapi.ts`。少写或多写说明，生成时都报错。
  - 批次请求、渲染请求与数据集的请求体就是 `schemas/` 里 DSL 1.0 的 JSON Schema，原样收录；镜像里因此带上 `schemas/`（`service/Dockerfile`、`.dockerignore`）。
  - 错误回答按状态放在 `components.responses`；推送清单与套餐两份请求 Schema 各端点共用，放进 `components.schemas`。
- **快照与兼容**：
  - 快照是 `docs/api/openapi.json`，描述变了就要 `npx vitest run -u` 显式更新；
  - 1.0.0 基线是 `docs/api/openapi-1.0.0.json`。`service/test/openapi-compat.ts` 列出相对基线不是加法的改动：删端点或参数、新增必填、收窄请求、回答删属性或放宽类型、必有变可有、改访问要求；
  - 描述与基线不同就要升版本，并在 `docs/api.md` 的变更记录里写一行。基线在票据 15 的阶段验收时定稿。
- **错误与状态**：`PROBLEM_STATUS` 把每个服务问题码对应到状态：400、401、403、404、409、413、415、429、500、503；引擎的问题码随 400，出图记录与存储不符随 500。核对办法见验证一节。
- **webhook**：
  - **管理**：客户管理员与 API 密钥都能管理，端点有五个：
    - `POST /v1/webhooks` 注册，签名密钥 `whsec_…` 只在回答里出现一次；
    - `GET /v1/webhooks`、`GET /v1/webhooks/{id}` 查看；
    - `PATCH /v1/webhooks/{id}` 停用、重新启用或改说明；
    - `GET /v1/webhooks/{id}/deliveries` 看投递记录，按 ID 倒序翻页，每条带各次尝试。
  - **URL 与上限**：URL 只收 https 与公网地址，答 400 `webhook.urlNotAllowed`；每个租户最多同时启用 10 个，超出答 409 `webhook.limitReached`。
  - **事件**：批次结束时，与发布批次清单同一个事务，记一个 `batch.finished` 事件，并给启用、订阅了它的每个 webhook 各记一条投递。正文是批次摘要：`outcome`、`summary` 与批次级问题，不含逐项结果。
  - **签名**：`RenderWeave-Signature: t=<秒>,v1=<HMAC-SHA256(密钥, "<t>.<正文>")>`，每次尝试用发送时刻重签；另带事件 ID、事件种类、投递 ID 与第几次尝试。
  - **投递任务**：在接口进程里，用属主函数 `rw_claim_webhook_deliveries` 跨租户领取到期的投递，带租约。2xx 算成功，不跟随重定向；失败按 1、2、4……64 分钟退避，共 8 次，试满记失败。连接前再查解析出的地址，挡住内网、回环与保留地址。
  - **密钥存放**：签名密钥用服务密钥 `RW_SECRET_KEY` 以 AES-256-GCM 加密、绑定租户后存库。`up.mjs` 在 `.env` 里补上这个变量，Compose 传给接口进程与 tester。
- **批次的 `outcome`**：批次结束后带 `outcome`，取值是 `completed`、`partiallyFailed`、`failed` 或 `cancelled`，与事件里的相同。
- **存储**：迁移 0008 加四张表：`webhooks`、`webhook_events`、`webhook_deliveries`、`webhook_attempts`。
  - 四张都开行级安全；
  - 事件与尝试只授 SELECT 与 INSERT，webhook 与投递不授 DELETE；
  - 另加领取函数。
- **后端接口**：
  - `TenantScope` 加 `createWebhook`、`listWebhooks`、`getWebhook`、`updateWebhook`、`listWebhookDeliveries`；
  - `ServiceBackend` 加 `webhooks`（`claim`、`record`）；
  - `ApiOptions` 加 `secretKey` 与 `allowPrivateWebhooks`。
- **配置**：
  - `RW_SECRET_KEY` 必填，64 位小写十六进制；
  - `RW_WEBHOOK_POLL_MS`、`RW_WEBHOOK_RETRY_BASE_MS`、`RW_WEBHOOK_MAX_ATTEMPTS`、`RW_WEBHOOK_TIMEOUT_MS` 有缺省值；
  - `RW_WEBHOOK_ALLOW_PRIVATE` 缺省 `false`。
- **文档**：
  - 新增 `docs/api.md`：鉴权、错误与状态、常用流程、webhook 的接收与签名校验、兼容策略、变更记录；
  - `docs/service.md` 加“开放 API 描述”与“webhook”两节，并同步配置、进程、批量交付与测试；
  - `GLOSSARY.md` 加“开放 API”“webhook”“投递”；
  - 记下 M276、M277。

**判断**

- **签名密钥每个 webhook 一个**：PRD 写的是“租户的签名密钥”，这里落实为租户名下、每个 webhook 各一把。一个租户的几个接收系统不共用钥匙。换钥匙就是注册新的、确认收得到再停用旧的，自然有过渡期，不必另做轮换端点。
- **密钥加密存放**：HMAC 要用明文，不能像 API 密钥那样只存哈希。加密后，单是库的备份泄露，伪造不了投递。代价是服务密钥要在各接口进程间共享；丢了就只能重新注册 webhook。
- **描述的回答部分手写，靠逐回答核对防漂移**：Fastify 的回答 Schema 会按 Schema 序列化，悄悄丢掉没声明的字段，所以不用它。改为在测试里把描述当作封闭的 Schema，核对每个回答。
- **基线现在就建、到票据 15 定稿**：v1.0 还没对外发布，后面的票据还可能加端点。加法不受影响；不兼容的改动要重写基线并在变更记录里注明，所以是显式的一步。
- **Docker 里由真实接口进程投递**：Compose 里的接口进程一直在跑，它的投递任务会领到 tester 记的投递。所以让 tester 与它用同一个服务密钥与同样缩短的退避，接收端监听 tester 在 Compose 网络里的地址。这样验的正是部署时的路径。
- **事件不含逐项结果**：一批最多 1,000 项，正文会很大。接收端要逐项结果时按批次 ID 取。

**没做**：

- 手动重投与按批次查投递；
- 别的事件种类；
- 签名密钥的轮换端点（注册新 webhook 即可）；
- 控制台的 webhook 管理页（票据 14）；
- OpenAPI 的文档站点。

**验证**

- **每个回答都按描述核对**（`service/test/openapi-check.ts`）：`createWorld` 发出的每个请求，回答都要满足四条，否则这次调用就失败：
  - 状态码在这个端点的描述里；
  - 媒体类型对；
  - JSON 正文符合描述，描述里的对象按封闭的核对；
  - 错误回答里每个严重问题的问题码与状态对应。

  两种后端的全部 API 用例都经过这道核对。接上之后第一轮只发现一处不符：签发代建令牌时指定的租户不存在会答 404，描述里漏了，已补上。
- **OpenAPI 合同用例**（`service/test/openapi.test.ts`，5 项）：
  - 描述覆盖全部已注册的路由，`operationId` 不重复，非公开端点都有 401，错误回答都引用问题清单，与快照相同；
  - Schema 在严格模式下都能编译；
  - 相对 1.0.0 基线只做了加法，版本号在 `docs/api.md` 的变更记录里；
  - 兼容检查本身：12 种不兼容的改动都认得出（删端点、请求新增必填、收紧取值范围、删请求属性、新增必填参数、回答删属性、放宽类型、必有变可有、删成功状态、事件正文删属性、改访问要求、收窄 DSL 请求），7 种加法都放过；
  - 逐个端点探查：61 个非公开端点不带令牌都答 401 `auth.required`；没有请求体、路径里有对象的端点，对象不存在时答 404；JSON 请求体给 `[]` 答 400（只校验的端点答 200 与问题清单）；未知的查询参数答 400。
- **webhook 用例**（`service/test/webhooks.test.ts`，10 项，测试进程里起投递任务，接收端在本机）：
  - 注册：客户管理员与 API 密钥都能注册。签名密钥是 `whsec_` 加 43 个字符，列表与查看里只有前缀。
  - 管理：停用、重新启用、改说明都记审计，审计里没有密钥。8 种不合规的注册与 3 种不合规的修改都答 400。
  - 上限：同时启用 10 个后再注册答 409；停用一个后能再注册；再启用一个停用的又答 409。
  - URL：生产配置下 http 的 URL，与 14 种本机、内网、链路本地、运营商 NAT、IPv6 唯一本地、IPv4 映射与 `localhost` 的 URL 都答 400，公网 https 能注册。
  - 投递一次：批次结束时两个启用的 webhook 各收到一次，停用的收不到，多等几轮也不多。正文与 `GET /v1/batches/{id}` 的摘要一致。
  - 签名：按文档独立核对 HMAC，用各自的密钥能通过，用对方的密钥、改过的正文都不通过；时间戳与收到时刻相差不到 5 秒。
  - 结果：全部交付、全部失败与取消三种结果各投递一次；投递记录能翻页。
  - 重试：接收端依次答 500、不回答、断开、204，记下 4 次尝试，结果依次是 500、超时、连接失败、204。相邻两次尝试的间隔不短于 150、300、600 毫秒；事件 ID 不变，每次重签，第几次尝试的头递增。
  - 试满：一直答 503 的试满 4 次记失败，之后不再投；答 302 的不跟随，不算收到。
  - 停用：投递进行中停用，排着的重试停下；重新启用后接着投，成功。
  - 出站地址：生产配置的投递任务不连 `127.0.0.1`，也不连解析到回环的 `localhost`，接收端一次都没收到。
  - 日志：没有签名密钥；投递失败的日志没有 URL 与正文。
- **配置**（`service/test/config.test.ts` 新增 1 项）：服务密钥必填、必须是 64 位小写十六进制，缺少或不合规时只报变量名；其余数值有缺省值。
- **权限矩阵与跨租户端点清单**：新加 5 个 webhook 端点与 `/v1/openapi.json`（公开）；矩阵与清单逐项通过，另一租户访问 A 的 webhook 与访问随机 ID 的回答逐字节相同。
- **Docker 后端**：`node service/scripts/test-docker.mjs` 从空环境起服务，13 个文件、107 项通过，服务日志 356 行都是合格的 JSON。
  - webhook 的同一组用例跑 PostgreSQL 加 S3（9 项）。投递由 Compose 里真实的接口进程完成，接收端在 tester 容器里。库里存的签名密钥都是 `v1.` 开头的密文，不含明文。
  - Compose 里的接口进程返回的 OpenAPI 描述与测试进程按同一份代码生成的相同。
  - 行级安全：四张新表都开启，漏写条件只返回当前租户。事件与尝试改不了、删不了，webhook 与投递删不了。
  - 第一次全量运行时，票据 09 的崩溃对账用例失败了：它把服务复制到新目录起进程，副本里没有 `schemas/`，而 OpenAPI 模块在启动时就读它。副本补上 `schemas/` 后通过；等不到就绪时的报错也改为带上进程最后几行日志。
- **变异检查**：
  - **内存后端 28 处，全部抓住**。改动包括：
    - 签名：不带时间戳；重试沿用旧时间戳；第几次尝试的头不变；密钥不绑定租户；
    - 重试：不重试；退避不翻倍；没有超时；3xx 算成功；
    - webhook 状态：停用的照样记投递；停用的照样领取；
    - 地址与上限：注册不查 URL；投递不查解析地址；不查 IP 字面量；注册与重新启用不限 10 个；
    - 事件与结果：事件带逐项结果；全部失败记成部分失败；取消不优先；
    - 日志：失败日志带 URL；
    - 描述：漏写 409；`Batch` 少写 `outcome`；问题码与状态对应错；不自动列 404；登录漏写 401；成员角色的枚举写错；URL 问题答 422；
    - 兼容检查：漏掉新增必填；漏掉回答删属性。

    另有 1 处无害的对照改动，照预期全过。
  - "3xx 算成功"第一轮存活：重定向用例只断言了第一次尝试记 302。补断言这条投递不是 `succeeded`、每次尝试都是 302 后，第二轮抓住。
  - **Docker 后端 5 处，都抓住**：停用的照样记投递、领取函数不看停用、注册不限 10 个、投递记录正序、重新启用不限 10 个。最后一处第一轮写成了编译不过的形式，改成能编译的再跑才算数。
