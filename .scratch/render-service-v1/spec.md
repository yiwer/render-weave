# 阶段 4 PRD：出图服务第一版（v1.0）

2026-10-19。第三阶段验收通过：代建模式可行，真人照指南从示例图走到正式出图约 30 分钟。开工前的难逆转事项已写成 ADR-0017–0020，部署、字体与计费的输入由用户定下（M240–M242）。本期把出图做成多租户服务，这是第一个收费版本 v1.0（M206、M207）。

## Problem Statement

RenderWeave 现在只能在一台机器上用命令行出图，离"卖给客户用"还缺五件事：

- **客户用不了。** 出图要写 JSON 请求、跑 `renderweave deliver`，客户不会写 DSL，也不会用命令行（M204）。日常价值在出图，可客户既没有填数据的表单，也没有 Excel 导入，看不到预览，也查不了出图记录。
- **没有租户。** 所有数据都在本机的工作区目录与资源仓库里，没有账号、没有鉴权，几个客户的数据无法分开，也无法审计。
- **执行没有隔离。** 渲染在命令行进程里串行执行，同步的 WASM 绘制打断不了，也没有单项超时与内存上限（[第二阶段验收](../../docs/stage2-acceptance.md#接入服务前必须补的验证)）。一个异常请求能卡死或拖垮整个进程。
- **存储绑死在本地文件系统。** 资源仓库靠写锁目录与重命名清单提交，出图记录靠排他目录与硬链接。换成数据库加对象存储，这些都要重新设计（第二阶段验收的"存储替代"）。
- **没有计量与额度。** 计费要按月额度计出图张数与 token 数（M242），现在无从计量，也无从拦截。

## Solution

在本机 Docker 上搭出完整的出图服务（M240）。

1. **存储接口**：引擎把工作区文档、资源仓库与出图记录三处存储抽成接口。命令行继续用本地文件实现，行为不变；服务端用 PostgreSQL 加 S3 协议的对象存储实现同一组接口（ADR-0018）。
2. **出图服务**：接口进程负责鉴权、校验、计额度、入队；渲染 worker 按进程隔离，带单项超时与内存上限（ADR-0017）。
3. **租户与开放 API**：客户组织是租户，有账号、角色、API 密钥与审计。开放 API 提供数据集、资源、草稿预览、批量交付、出图记录与用量，批次结束发 webhook。
4. **出图记录**：按内容哈希存入对象存储，跨批次去重；可以导出，导出后用命令行离线重放；重放按构建标识找确切构建（ADR-0019）。
5. **计量与额度**：按月额度计正式交付的张数与代建的 token；批量交付先预占、逐项结算（ADR-0020）。
6. **代建导入**：代建工程师照第三阶段的命令行流程在本机做好数据定义、模板与资源，再用一条命令推送到客户的租户（ADR-0017：v1.0 服务端不托管 Agent）。
7. **出图控制台**：客户在网页上按数据定义生成的表单填数据或导入 Excel，看草稿预览、调对外参数、批量交付、下载图片、查询与导出出图记录（原型 C）。

### 完成标准

在本机用 Docker Compose 从空环境起完整服务，走完以下流程：

平台管理员建租户与套餐 → 代建工程师把本地做好的数据定义、模板与资源推送到该租户 → 客户操作员登录出图控制台，用表单填一份数据、用 Excel 导入一批数据 → 看草稿预览、调对外参数 → 批量正式交付 → 下载图片，导出出图记录，用 `renderweave replay` 离线重放成功 → 用量与剩余额度正确，超额时整批被拒绝。

客户开发者用 API 密钥经开放 API 走同样的交付流程，收到签名的 webhook。全程不手工改数据库、不手工复制文件。同时给出容量基线，现有测试与样例没有回归。

## Implementation Decisions

### 存储接口（ADR-0018）

- **三处抽象**：引擎把工作区文档的读取、版本化资源仓库、出图记录（交付、读取、批次读取与重放）抽成不依赖框架的接口，留在引擎内。渲染入口本来就只接收内存中的工作区，不受影响。
- **三种实现**：
  - 本地文件实现留作命令行后端，现有行为、文件布局与测试不变（A01）；
  - 内存实现供测试与服务的快速测试使用；
  - PostgreSQL 加 S3 的实现放在服务里。
- **批量交付拆成两步**：
  - **固定**：校验外层、固定文档与资源版本，把固定后的输入存成批次快照；
  - **交付单项**：按批次快照渲染一项，产出记录内容，经接口提交。
  
  本地命令行仍按顺序调用这两步，外部行为不变；服务端把单项分给多个 worker。M153 的批次语义不变：外层非法整批拒绝、单项失败不影响其他项、运行中的修改不混入本批。
- **资源仓库**：语义与 `renderweave-resources/1` 一致（ID 与种类固定、内容版本递增、替换先检查影响再按预期版本应用）。服务端的提交点是带预期版本条件的数据库事务。
- **文档**：按原始字节存，数据库只记种类、名称、版本与哈希，保证 M112 的精度检查与出图记录内容不变。

### 服务结构（ADR-0017）

- **三部分**：接口进程、PostgreSQL 里的任务队列、渲染 worker 容器。每个 worker 容器有一个调度进程和一个渲染子进程，一次只做一项；超时由调度进程结束子进程，内存上限用容器限制。
- **服务代码**放在仓库内单独的服务目录，不进引擎源码目录；只经引擎的公开入口调用。HTTP 框架由实施选定，外壳只做鉴权、校验、计额度与入队。
- **批次按构建固定**：一个批次只由接受它的那个构建的 worker 处理。滚动发布时旧 worker 做完已接受的批次再退出。
- **单项超时、内存上限与 worker 复用项数**的数值由容量基线实测后定，写进配置与文档。
- **入队前的限制**在接口进程检查，用引擎的纯函数，不出图：请求与数据集字节数、批量项数（1,000，M153）、单张最大像素（套餐值，且不超过引擎上限）、循环展开后的项数与元素数。

### 租户、账号与鉴权

- **租户**是一个客户组织，v1.0 每个租户一个工作区与一个资源仓库。切换条件：客户需要分产品线隔离数据时，在租户下加"项目"。
- **账号**：成员账号由平台管理员创建，邮箱加密码登录，密码以慢哈希保存；不做自助注册、第三方登录与邮件找回，密码由管理员重置。
- **客户角色**：
  - 管理员：有操作员的全部权限，另外管理成员、API 密钥与 webhook，替换已有资源，查看用量与审计；
  - 操作员：管理数据集，上传新的图片与字体资源，预览、交付与查询记录。
- **内部角色**：平台管理员管理租户与套餐；代建工程师只能对指定租户推送与预览。跨租户操作一律记审计。
- **API 密钥**属于租户，只存哈希，创建时显示一次，可吊销。带密钥的请求有操作员的全部权限，另加 webhook 管理；不能管理成员与密钥，也不能替换已有资源。
- **隔离的两道防线**（ADR-0018）：鉴权后只拿到本租户的存储句柄，客户端不能提交对象键或路径；每张租户表开行级安全，每个事务设置当前租户。
- **审计**：写操作与跨租户操作追加写入审计日志，记录人、租户、操作、对象与时间，不记业务数据内容与密钥。

### 开放 API

- **基本形态**：JSON over HTTP，路径带主版本 `/v1`，提供 OpenAPI 描述。1.x 只做向后兼容的加法，比照 ADR-0016 对 DSL 的承诺。
- **资源**：
  - 数据定义与模板只读（由代建推送）；
  - 数据集读写；
  - 图片与字体资源：上传、列出、替换检查、应用替换；
  - 草稿预览：同步返回图片与问题清单，不计额度，限频；
  - 批量交付：异步，带幂等键，可查状态、逐项结果、取消；
  - 出图记录：查询、下载图片、导出；
  - 用量；webhook 注册与投递记录。
- **正式图只走批量交付**：单张也按一项的批次交付，所以每张正式图都有出图记录（M154），也都计费（ADR-0020）。
- **错误**一律带问题清单，格式与引擎的问题一致（问题码、等级、位置、说明）。HTTP 状态按类别映射：请求不合法 400、未鉴权 401、无权限 403、不存在 404、冲突 409、额度不足或限频 429。
- **问题码对齐**（M203 遗留）：批量项找不到数据集或静态定义时，报与单次渲染相同的精确问题码，不再统一报 `record.invalid`。这是开放 API 之前对命令行的一处行为修正，按 ADR-0016 的缺陷修正口径统计影响并记录。
- **webhook**：批次结束（完成、部分失败、取消）时投递，正文带批次摘要。用租户的签名密钥对正文做 HMAC 签名，附时间戳防重放；失败按指数退避重试有限次，投递记录可查。

### 出图记录（ADR-0019）

- **格式不变**：内容与语义沿用 `renderweave-output-record/1`。文件按 SHA-256 存为本租户的对象，记录行是提交点，与计费在同一事务。
- **导出**：按项或按批次导出的目录结构、文件名与内容，与本地 `deliver` 的成果一致，能直接用 `renderweave record-read` 与 `renderweave replay` 核对和重放。
- **重放**按记录的构建标识交给对应镜像的 worker。镜像不在时拒绝，问题说明写明缺哪个构建。
- **v1.0 不删除记录**，不回收未登记的对象，也不接收外部导入的记录。

### 计量与额度（ADR-0020）

- **计数口径**：正式交付成功一项计 1 张。失败、未执行、草稿预览与重放不计；草稿预览与重放只限并发与频率。
- **预占与结算**：提交批次时在一个事务里锁当期计数行，额度不够整批拒绝（`quota.exceeded`，429，说明里写剩余额度）。逐项成功时与记录行同一事务结算，失败与未执行退回预占，批次结束退回剩余预占。对账任务回收崩溃后遗留的预占。
- **token**：代建推送时随附各轮的用量（输入、输出、缓存读、缓存写），记为用量事件，v1.0 不拦截。
- **周期与套餐**：周期是自然月，按 UTC+8 切分，不结转；套餐（月张数、单张最大像素、并发数）由平台管理员设置。

### 代建导入

- 命令行新增推送命令：把本地工作区与资源仓库推送到指定租户，凭代建工程师的令牌鉴权，令牌只经环境变量传入（与模型 key 的规则一致）。
- **推送前先计算差异**：新增、更新、冲突。静态数据定义同名同版本内容不同是冲突；资源按 ID 对比内容版本。有冲突就整体拒绝，没有冲突就在一个事务里提交。
- **模板**每次推送记新修订，按名称指向当前修订；可以回到旧修订。
- **用量**：可选附带轮次目录，读取各轮 `round.json` 的用量记到该租户。

### 出图控制台

- **定位**：网页是开放 API 的客户端，不另开后端接口，由接口进程作为静态文件提供。前端框架由实施选定，缺省 React 加 Vite。
- **表单生成**：表单由静态数据定义的编译产物生成，字段用显示名称，校验结果以引擎的问题清单为准（提交到服务端校验），不在前端另写一套校验规则。
- **Excel 导入**在服务端解析，一行对应一个渲染项：
  - 列对应顶层字段，可以写显示名称或字段名称；
  - 简单类型的列表用分隔符写在一格；
  - 一层数据定义引用的列表（例如站点）写在另一张表，用关联列对应主表的行。
  - 结果是数据集与批量请求的预览，加逐行问题清单；确认后才提交。
  - 切换条件：客户的表格结构超出这两种写法时，再加映射配置。
- **预览**：调用草稿预览接口，问题位置叠加在图上，对外参数用参数面板调整。
- **记录**：按时间、模板、批次查询，下载图片与压缩包，导出记录。
- **语言**：界面只做中文。

### 部署与运维

- **环境**：Docker Compose 起接口进程、worker、PostgreSQL 与 S3 兼容的对象存储，从空环境一条命令启动。服务只用 S3 的基础对象操作。
- **配置**：数据库与对象存储的凭据、签名密钥只经环境变量传入，不写进镜像与仓库。
- **数据库迁移**按版本号顺序执行，启动时检查。
- **可观测**：结构化日志，接口进程与 worker 的健康检查，指标包括队列积压、渲染用时、超时与内存超限次数。
- **镜像**以构建标识打标签并保留，供重放使用（ADR-0019）。

## Testing Decisions

### 接缝与既有实践

本期只有两个测试接缝：

1. **引擎的公开入口**（沿用）。存储接口重构后，现有测试全部不改、全部通过，是兼容的主要证据。另加一组存储接口合同测试，对本地、内存，以及 PostgreSQL 加 S3 三种实现跑同一组用例，覆盖资源版本的提交与冲突、批次快照、记录提交与读取。
2. **服务的开放 API**（新增，主接缝）。服务测试只经 HTTP 请求驱动，断言响应、问题清单，以及经 API 可见的结果（批次状态、记录、用量、审计）。同一组用例跑两种后端：
   - **内存后端加进程内 worker**：进 `npm test`，覆盖 API 合同、租户与权限矩阵、额度、幂等、webhook 签名与重试、代建推送的差异与冲突、Excel 导入；
   - **Docker 后端**：PostgreSQL、S3 兼容存储与真实的 worker 进程，与 Linux 全量测试一样单独运行。只在这里测的有：行级安全、单项超时与内存超限的恢复、按构建路由重放、对账回收预占、容量基线。

其余约定：

- **API 合同**：OpenAPI 描述做快照测试，比照 MCP 工具合同的快照；任何变化都要显式更新快照，并判断是否兼容。
- **出图控制台**：少量浏览器端到端测试，走完成标准中的主路径，放在 Docker 后端那组；外加一次真人走查。
- **离线重放**：导出的记录交给命令行的 `record-read` 与 `replay` 断言成功，这是记录自足的直接证据。
- **好的测试**给业务输入，断言能否交付、交付了什么、哪里被拒绝、额度怎样变化、别的租户能否看到；不断言私有模块、表结构与调用次数。
- **既有实践**：
  - MCP 合同与快照测试，经 JSON-RPC 客户端驱动服务；
  - 批量交付、出图记录、重放、批次读取与资源替换的测试；
  - 审核页的本机 HTTP 测试；
  - 1,000 项长批次的内存回归脚本；
  - 资源清单提交压测脚本；
  - Linux 容器全量测试的做法（[开发环境与接续](../../docs/dev-setup.md)）。

### 验收矩阵

| 编号 | 场景与观察点 | 通过条件 |
|---|---|---|
| A01 | 兼容 | 现有测试全部通过；命令行的出图、交付、重放、资源维护行为与文件布局不变；共享 M402 样例、基准图片、布局摘要与已有出图记录的重放结果没有变化。问题码对齐按 ADR-0016 的缺陷修正口径统计影响并记录 |
| A02 | 存储接口 | 三处存储都经接口访问；本地、内存，以及 PostgreSQL 加 S3 三种实现通过同一组合同测试；批量交付拆成"固定"与"交付单项"后，批次语义与 M153 一致 |
| A03 | 租户隔离 | 对每个 API 端点，用另一租户的身份与密钥访问都被拒绝且不泄露存在性；绕过应用层直接查询时，行级安全仍挡住其他租户的行；客户端无法提交对象键或路径；跨租户操作都有审计 |
| A04 | 鉴权与角色 | 管理员、操作员、API 密钥、代建工程师、平台管理员的权限矩阵逐项覆盖；密钥只显示一次、可吊销，吊销后立即失效；仓库与日志中扫描 key 与密钥命中 0 |
| A05 | 代建推送 | 推送前给出差异；冲突整体拒绝且服务端不变；静态数据定义不可变；模板记修订且可回退；附带的轮次用量记到租户 |
| A06 | 开放 API 与问题码 | OpenAPI 快照稳定；草稿预览同步返回图片与问题清单；批量交付异步、可查进度与逐项结果、可取消；错误一律带问题清单且状态码映射正确；批量项与单次渲染对同一问题给出同一问题码 |
| A07 | 执行隔离 | 超时的一项被结束并标为失败、不计费，worker 自动恢复，同批其他项照常完成；内存超限的子进程被结束，结果同上；超出限制的请求在入队前被拒，不占 worker |
| A08 | 出图记录 | 相同字节在同一租户内只存一份，跨批次也是；导出包能用 `record-read` 与 `replay` 离线通过；重放交给记录所属构建的 worker，构建不在时拒绝并说明缺哪个构建 |
| A09 | 额度 | 预占、整批拒绝（429 加剩余额度）、逐项结算、退回预占都正确；同一幂等键重试不重复交付也不重复计费；worker 重领同一项只计费一次；崩溃后对账回收预占；草稿与重放不计额度 |
| A10 | webhook | 批次结束时投递一次带签名的事件，签名与时间戳可校验；失败按退避重试，投递记录可查 |
| A11 | 出图控制台 | 表单覆盖全部字段类型且以服务端问题清单为准；Excel 两种写法导入正确、逐行报问题；预览、参数面板、批量交付、下载与记录导出可用；真人走查记录用时与卡点 |
| A12 | 环境、容量与跨平台 | Docker Compose 从空环境一条命令起服务，完成标准的全流程通过；给出每个 worker 的 CPU 与内存预算、单项超时、并发数，以及长期负载下的内存与延迟表现；`npm test` 在 Windows 与 Linux 上通过，Docker 后端那组在 Linux 容器上通过 |

## Out of Scope

- **托管业务 Agent**：代建工作台（原型 D）、每轮一个容器、网络化的 MCP、按轮签发凭据（M243、ADR-0017），以及供客户自己的 Agent 使用的 MCP 入口。
- **客户自助做模板**（阶段 5）：点选元素做小改、示例图向导、提案审批、组件库。控制台里的模板只读，只能调对外参数。
- **计费周边**：在线支付、自助注册、发票、按像素加权计价、token 额度拦截（ADR-0020）。
- **账号周边**：第三方登录、单点登录、邮件找回密码、多语言界面。
- **数据生命周期**：删除出图记录与回收对象、外部记录导入、跨租户共享资源或模板。
- **DSL 新能力**：由并行的 DSL 1.x 平面设计能力规格推进，本期不改 DSL。
- **上线**：真实云上部署、多地域与高可用、上线手续（M240，由用户办理）。

### 实施顺序

1. 存储接口：三处接口与内存实现；批量交付拆成"固定"与"交付单项"；本地行为不变。
2. 服务骨架：Docker Compose、数据库迁移、PostgreSQL 加 S3 的存储实现与合同测试。
3. 租户、账号、角色、API 密钥、行级安全与审计。
4. 渲染 worker 与任务队列：草稿预览、批量交付、超时与内存上限、取消、按构建固定批次；问题码对齐。
5. 出图记录进对象存储：提交、去重、导出、按构建重放。
6. 计量与额度：预占、结算、对账、用量查询。
7. 代建推送命令。
8. 开放 API 收尾：OpenAPI 快照、webhook、幂等。
9. 出图控制台：登录、模板与参数面板、表单、Excel 导入、预览、批量交付、记录。
10. 容量基线与阶段验收：端到端流程、真人走查、两轴审查。

以上是依赖顺序，票据拆分后列在本目录的 README。接口内部组织交给实施，外部行为与验收条件以本文为准。2026-10-19 用户确认本规格与测试接缝，规划决定登记为 M244–M249。

### 与并行工作的关系

DSL 1.x 平面设计能力（[规格](../dsl-graphic-capabilities/spec.md)）在另一台设备上推进，主要改模板解析、求值与排版；本期第 1 步改的是存储与交付。两边都会改引擎，交点是批量交付与出图记录的输入准备。按提交顺序处理：先合入的一方不受影响，后合入的一方负责 rebase 并跑全量测试。
