# 出图服务由接口进程、任务队列与渲染 worker 进程组成，隔离单位是进程

阶段 4 的出图服务分三部分：

- **接口进程**：负责鉴权、校验请求、检查额度，然后把渲染任务写进队列。它自己不渲染。
- **任务队列**：放在 PostgreSQL 里，worker 用 `SELECT … FOR UPDATE SKIP LOCKED` 领取任务。
- **渲染 worker**：每个 worker 容器里有一个调度进程和一个渲染子进程，同一时间只做一项。调度进程领取任务，交给渲染子进程，超时就杀掉子进程，再起一个新的。内存上限用容器的内存限制。

服务代码放在仓库的 `service/` 目录，不进 `src/`（CODING_STANDARDS「引擎边界」），只经引擎的公开入口 `src/index.ts` 调用渲染、交付与重放。HTTP 框架不在本 ADR 定：外壳只做鉴权、校验与入队，换框架不影响引擎与 worker。

## 为什么隔离单位是进程

第二阶段验收把执行隔离列为接入服务前必须补的验证（[第二阶段验收](../stage2-acceptance.md#接入服务前必须补的验证)）。2026-10-19 在 Node v24.21.0 上实测了 worker 线程，结论如下：

- **线程能管住时间**：主线程调用 `worker.terminate()`，200 ms 内打断了线程里正在跑的 WASM 死循环。
- **线程管不住内存**：给线程设 `resourceLimits.maxOldGenerationSizeMb: 32`，线程里照样申请并写满了 1024 MB 的 `WebAssembly.Memory`。CanvasKit 与 resvg 的内存都在 WASM 里，所以线程的限制对它们无效。
- **WASM 内存耗尽会拖垮同进程的其他渲染**：WASM 内存耗尽时整个进程退出，同一进程里的其他渲染跟着失败（推断，未实测）。

所以隔离单位定为进程。一个渲染子进程同时只跑一项。

- **复用**：子进程在任务之间复用，省去每次加载 CanvasKit 的时间。超时、崩溃或做满一定项数后换新进程。
- **数值**：单项超时与内存上限的具体数值，在实现票据里按 M402、价签与 1,000 项长批次的实测来定。

## 进入队列前的限制

能在入队前拦住的都在接口进程拦住，不占 worker：

- 请求与数据集的字节数；
- 批量项数（沿用 1,000，M153）；
- 单张图的最大像素：套餐限定的上限（M242），且不超过引擎现有上限（单边 20,000 px、总数 1 亿）；
- 循环展开后的项数与元素数。

这些检查用引擎的纯函数做，不出图。

## 批量交付

- **拆分与汇总**：一批拆成逐项任务，由 worker 并行领取，跨项的状态保存在数据库里。全部项结束后，由汇总步骤写批次清单。
- **语义不变**：沿用 M153，即外层非法整批拒绝、单项失败不影响其他项、启动前固定文档与资源版本。
- **取消更彻底**：本地版本只能在项与项之间取消（同步绘制打断不了）；服务版本可以杀掉正在渲染的子进程。

## 模型不在出图路径上

给客户出图是引擎的确定性渲染，不调用任何模型。

v1.0 的服务端不托管业务 Agent，代建照第三阶段的做法进行：内部团队在自己的机器上用 `renderweave agent` 完成提取、审核与应用，经服务的导入接口把数据定义、模板与资源写进客户的租户。

- **理由**：还没有客户，代建量很小，第三阶段的命令行流程已经验收（真人约 30 分钟到正式出图）；托管 Agent 要先补 ADR-0015 列出的四项（每轮一个容器、网络化的 MCP、按轮签发凭据、并发与额度），成本大，收益要等代建量上来才有。
- **切换条件**：代建排期跟不上、命令行流程成为瓶颈，或者到阶段 5 向客户开放 Agent。到那时再做路线图里的代建工作台（原型 D），ADR-0015 的四项随之补上。
- **模型提供方**：仍按 ADR-0015 与 M232，模型由端点与模型名决定，换模型用同一套评估门槛判断（M230）。

## 开发环境

本机用 Docker Compose 起接口进程、worker、PostgreSQL 与一个 S3 兼容的对象存储（M240）。服务只用 S3 的基础对象操作，不依赖某一家实现的扩展。

## 代价

- 组件从一个命令行进程变成四类容器，部署与排障更复杂。
- 队列放在 PostgreSQL 里，吞吐比专用消息队列低；对 v1.0 的量足够。切换条件：领取任务的延迟或数据库负载成为瓶颈，再换专用队列，接口进程与 worker 的分工不变。
- 一个容器同时只渲染一项，并发靠容器数量扩展，空闲时占用的内存比线程池多。

依据：M153、M204–M207、M240、M242；ADR-0011（引擎不依赖框架）、ADR-0013（出图记录）、ADR-0015（Agent 运行方式）；[第二阶段验收](../stage2-acceptance.md#接入服务前必须补的验证)。实测脚本：`node scripts/probe-worker-isolation.mjs`。
