# 一切数据归属一个租户；PostgreSQL 记元数据与提交点，S3 存不可变字节；引擎经接口访问存储

v1.0 的租户是一个客户组织。用户只属于一个租户。我们的内部人员可以跨租户，但只做代建导入与运维，每次跨租户操作都记审计。每份数据都只属于一个租户，v1.0 不在租户之间共享任何东西。

存储分两层：

- **PostgreSQL**：记租户、用户、文档索引、资源版本、批次与出图记录的元数据，以及计量（ADR-0020）。数据库事务是唯一的提交点。
- **S3 协议的对象存储**（M240）：只存不可变的字节，按内容寻址，键是 `tenants/<租户>/blobs/sha256/<哈希>`。先写对象并核对哈希，再在事务里登记。没登记的对象不会被任何读者看到。

## 文档按原始字节保存

数据定义、编译产物、模板与数据集都按上传时的原始字节存成对象，数据库只记种类、名称、版本与哈希，不用 `jsonb` 存文档本身。

- **原因**：`jsonb` 会重排键、去掉重复键，也不保留数值原文。M112 要求发现超过 15 位有效数字的数值，出图记录要保存当时的文档内容（ADR-0013），这些都依赖原文。
- **版本规则沿用现有决定**：静态数据定义发布后不可变（ADR-0008）。模板每次导入记一个新修订，按名称指向当前修订，旧修订保留；这只是存储层的历史，不给模板加领域版本（ADR-0013）。

## 资源仓库换实现，不换语义

`renderweave-resources/1` 的语义原样保留：

- 资源 ID 与种类固定；
- 内容版本从 1 递增，哈希不代替版本号；
- 替换前检查影响，应用时核对预期版本（ADR-0014、M152）。

变的是实现：

- **提交点**：本地的"写锁目录加重命名清单"，换成数据库事务里带预期版本条件的更新。
- **内容**：内容文件换成按哈希寻址的对象，同一租户内相同字节只存一份。

我们自带的缺省字体（思源黑体）在建租户时导入该租户的资源仓库，与客户上传的字体同样处理（M241）。

## 引擎经接口访问存储

渲染入口已经只接收内存中的 `Workspace` 与 `ResourceRepository`（`src/workspace.ts` 头注释预留了"从数据库组装"），不碰存储。还直接读写本地文件的是三处：

- 工作区文档的读取；
- 资源版本仓库；
- 批量交付、读取与重放。

做法：

- **接口留在引擎里**：在 `src/` 中把这三处抽成不依赖框架的接口。本地文件实现留作命令行的后端，行为与现有测试不变。
- **服务端实现放在 `service/`**：用 PostgreSQL 与 S3 实现同一组接口。
- **测试**：引擎测试用内存实现，仍在 `npm test` 里跑。PostgreSQL 与 S3 的实现由单独的 Docker 测试覆盖，与 Linux 全量测试一样不进 `npm test`。

## 隔离的两道防线

1. **应用层**：鉴权之后只拿到本租户的存储句柄，对象键与查询条件都由句柄生成。客户端永远不能提交对象键或路径。
2. **数据库**：每张租户表都有 `tenant_id`，并开启行级安全（RLS），每个事务设置当前租户。应用层写错查询时，数据库也不返回别的租户的行。

写操作与跨租户操作记追加式的审计日志。

## 没有选的做法

- **跨租户按哈希去重**：只有缺省字体能省空间，却让删除租户与证明隔离变复杂，还可能经时序泄露"某内容在别处存在"。
- **把文档存进 `jsonb`**：原因见上。
- **对象存储自己做提交点**（条件写入、清单对象）：各家 S3 兼容实现对条件写入的支持不一，数据库事务更确定。

## 代价

- 服务端每类数据都要同时改数据库与对象存储，必须遵守"先写对象、再登记"的顺序。
- 进程在两步之间崩溃会留下没登记的对象，要靠以后的回收清理。v1.0 不删除数据，回收以后再做。
- 行级安全要求每个事务都设置租户，连接池里遗漏设置就查不到数据。这是故意的：宁可查不到，不可查错。
