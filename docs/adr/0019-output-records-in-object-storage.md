# 出图记录的格式不变，文件按内容哈希存入对象存储，提交点是数据库事务；导出后仍能离线重放

服务端的出图记录沿用 `renderweave-output-record/1` 的内容与语义（ADR-0013、M154）：

- 模板调用闭包、数据集、静态定义与编译产物、请求与选项；
- 资源内容版本与实际字节；
- 渲染器构建标识，以及结果摘要。

变的只是存放方式。

## 存放与提交

- **文件**：记录里的每个文件，包括 `input.json`、图片、`problems.json`、`layout.json` 与资源副本，都按 SHA-256 存成本租户的对象（ADR-0018）。`record.json` 本身也存成对象。
- **提交点**：worker 先写完并核对全部对象，再在一个数据库事务里写入记录行。记录行包含项标识、批次、构建标识与 `record.json` 的哈希；这个事务同时完成计费（ADR-0020）。事务提交之前，这一项对任何读者都不存在。
- **批次**：本地的 `batch.json` 与各项目录，改成数据库里的批次行与逐项状态。`batch-read` 那套"没有清单也能辨认已完成项"的语义，由逐项提交自然得到。
- **去重**：同一租户内相同字节只存一份，跨批次也去重。这实现了 M188 当时的推断：接入服务后，按哈希去重由存储层承担。本地同批硬链接（M194）只留在命令行后端。

## 记录可以导出，导出后自足

接口提供按项或按批次导出。导出的目录结构、文件名与内容，和本地 `deliver` 交出的一致：项目录里有 `record.json` 与它列出的文件，批次另有 `batch.json`。拿到导出包，就能用 `renderweave record-read` 与 `renderweave replay` 离线核对和重放，不依赖我们的服务。

"记录自足、可以重放"是对外的合规卖点（路线图），对象存储里的拆分存放不能削弱它。v1.0 不接收外部导入的记录，所以不用另防不受信任的记录。

## 按构建保留 worker 镜像，重放时找确切构建

ADR-0013 规定记录只由确切构建重放。在服务端，每次发布的 worker 镜像都以构建标识为标签保留。重放任务按记录里的构建标识交给对应镜像的 worker；镜像已不在时拒绝重放，不尝试由新引擎"尽量还原"，与本地行为一致。只要还有保留中的记录引用某个构建，它的镜像就不删。

不这样做的话，每次升级引擎都会让全部历史记录无法重放，合规卖点在第一次升级时就失效。

## 幂等与重试

- **批量提交**：带幂等键，客户端重试时返回同一批次，不重复交付，也不重复计费。
- **单项提交**：以"批次加项序号"为唯一键。worker 崩溃后重领同一项，最多重写相同的对象，记录行只会提交一次。

## 没有选的做法

- **记录整体打包成一个对象**：同一租户内跨批次去重就做不成了。M402 每项都带相同的字体，35 项会重复存 35 份。
- **对象存储里的清单对象作提交点**：理由同 ADR-0018。

## 代价

- 读一条记录要先查数据库，再取多个对象；导出要按记录重新组装目录。
- 镜像要长期保留，占用镜像仓库空间。
- v1.0 不删除记录，也不回收没登记的对象。以后做删除时，要用引用计数或标记清除，并给刚写入、尚未登记的对象留宽限期。
