# 按月额度计量出图张数与 token；批量交付先预占，交付与计费在同一事务提交

M242 定了计费方式：参考大模型厂商，每个租户每月有额度，计量出图张数与 token 数。本 ADR 定实现口径。

## 计什么

| 用量 | 计入额度 | 说明 |
|---|---|---|
| 正式交付成功的一项 | 1 张 | 只有正式交付产生出图记录（M154）。服务端的单次出图接口只出草稿，正式图一律走交付 |
| 失败项、取消后未执行的项 | 不计 | |
| 草稿预览、记录重放 | 不计 | 只限并发与频率 |
| 代建的 token | 记账，v1.0 不拦截 | 按输入、输出、缓存读、缓存写分开记。阶段 5 客户自己用 Agent 时再按额度拦截 |

- **大幅面**：先不按像素加权。套餐里有单张最大像素，接口进程在入队前检查（ADR-0017）。大幅面客户明显更耗算力时，再改为按像素加权。
- **token 的来源**：v1.0 的服务端不托管 Agent（ADR-0017），代建在团队机器上进行。每轮的 `round.json` 已记有 token（`RoundUsage`：`inputTokens`、`outputTokens`、`cacheReadTokens`、`cacheCreationTokens`）。导入代建成果时，一并提交这些轮次的用量，记到该租户名下。

## 怎么记

- **用量事件**：追加写入数据库，不改不删。每条有租户、计费周期、种类、数量、出处（批次与项、或代建轮次）与时间。
- **当期计数**：每个租户每个周期一行，记限额、已用与预占。
- **周期**：自然月，按 UTC+8 切分，不结转。客户主要在其他时区时再改为按租户设置。
- **套餐**：由管理员手工设置，不接在线支付（M242）。

## 批量交付：先预占，再结算

1. **提交批次时**：在一个事务里锁住该租户的当期计数行，检查"已用 + 预占 + 本批项数 ≤ 限额"。够就预占本批项数，不够就整批拒绝。拒绝时问题码为 `quota.exceeded`，说明里写剩余额度，HTTP 状态 429。不做"能交几项交几项"：部分交付会让客户难以对账，与 M153"外层错误整批拒绝"一致。
2. **每项正式交付成功时**：在提交记录行的同一个事务里（ADR-0019），写一条用量事件，已用加 1、预占减 1。交付成功与计费要么都发生，要么都不发生；worker 重试只会提交一次，所以不会重复计费。
3. **项失败或未执行时**：预占减 1。
4. **批次结束时**：退回剩余预占。预占记在批次上；worker 或接口进程崩溃后，由对账任务找出已结束或已超时的批次，退回它们的预占。

## 没有选的做法

- **交付后再扣、允许超额**：月底账单不可预期，额度也就不起作用。
- **每项开始前逐项检查额度**：批次可能做到一半因额度停下，与 M153 的批次语义冲突。
- **草稿也计数**：做模板、调参数要反复预览，计数会让客户不敢预览。用频率限制控制成本就够了。

## 代价

- 预占使批次进行中可用的额度变少。一批最多 1,000 项（M153），影响有限。
- 计费与记录提交绑在同一个数据库里。以后把记录与计费拆到不同的库，要改成可靠消息加对账。
- token 在 v1.0 只记不拦。如果代建的 token 成本需要转嫁给客户，账单要另外按事件汇总。

依据：M153、M154、M204、M206、M242；ADR-0017、ADR-0018、ADR-0019。
