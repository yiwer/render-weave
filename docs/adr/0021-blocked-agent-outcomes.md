# 受阻成果可以交回，正式交付仍须通过渲染与人工审核

阿拉伯文复跑中，静态合法的模板实际渲染报 `text.unshapedScript`，Agent 又被要求消除严重问题才交回，最终在周额度耗尽前没有保存 outcome。用户要求先落实成果评估、中断草稿与硬额度停止（M277、M278）。

## 决定

成果评估分开记录结构、候选校验、内容待审核与指定请求的实际渲染。`qualified` 是技术检查结论，不表示信息完整或视觉还原合格。模板存在渲染严重问题时为 `unqualified`；数据集提取的预览继续只作参考（M52）。缺少完整请求时明确 `notChecked`。

Agent 尽早保存 `outcome.json`。已知引擎能力阻塞可以交回候选与说明，审核页展示草稿；保留 severe，禁止批准与应用。应用前在当前工作区再渲染，避免审核之后数据变化却沿用旧结论。

未交回有效 outcome 时，宿主把已写完整的候选和哈希保存为独立 `draft.json`，标明 `hostRecovery`。损坏文件仍留在原工作目录，恢复草稿只供查看和下一轮接续。宿主不知道 Agent 的完成度和待确认项，因此不补造正式提交，也不允许直接批准。

运行层只将明确的硬额度错误视为终止条件。Google 转换代理在首次确认后封住后续上游调用，并通知宿主停止本轮执行器进程树；直连运行时明确报告同类错误时也停止。一般 429、5xx 不据此停止。停止后仍执行成果保存并给出续跑入口；不切换模型、不自动等待或重试。

## 取舍

交回检查多做一次渲染，增加本地耗时，但能在昂贵的模型修复循环前暴露真实阻塞。保留两种成果文件增加读取分支，换来明确的来源与审核边界。直连 Claude Code 若仅给出 `rate_limit` 而没有错误正文，不能判断是否硬额度；保持运行时原有退避，真实链路验收见票据 38。

本次不引入 OCR，也不以模型自评取代内容或样式核查；这些分别在票据 33、34、36 验证。
