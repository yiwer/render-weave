### 字号偏小的追加诊断（2026-10-21）

直接原因已验证：模型初次写 `stop-row.json` 时就把普通站名设成 5.5 mm、英文副标题设成 3.6 mm，最终保留了这些值（本轮 `logs/stream.jsonl:99`；候选 `stop-row.json:1067`、`:1113`）。不是自动适配把大字缩成了小字。

运行 `node out/arabic-board-retest-2026-10-20/diagnostics/font-size.mjs`，经公开渲染入口比较同一模板与数据：

| 对照 | 普通站名实际字号 | 实际文字宽 × 高（mm） | 压缩比 / 溢出 |
|---|---:|---|---|
| 原候选，50 DPI | 5.5 | 44.685 × 5.162 | 1 / false |
| 仅把普通站名字号改为 11，50 DPI | 11 | 89.370 × 10.323 | 1 / false |
| 原候选，100 DPI | 5.5 | 44.685 × 5.162 | 1 / false |

三组均无额外严重问题，字号加倍也放得下。DPI 只把图片从 1575×1772 变成 3150×3543 像素，没有改变文字的物理尺寸与版面比例。11 mm 是定位原因的对照值，不是已经完成设计验收的最终字号；对照只修改普通站名，本站状态字号与其他文字保持原样。原候选未修改，诊断图和 JSON 在 `diagnostics/`。

判断：这次是 Agent 的初始字号估计偏小，且没有完成尺寸校准与视觉纠偏。任务资料已要求查字号与压缩比（`agent/tasks/template-design.md:20`），领域资料给了默认站名 10 mm（`agent/domains/route-sign.md:20`），但本轮 `inspect_layout` 调用为 0。检查能发现溢出，不能判断相对参考图是否过小，因此偏差未被结构检查发现。额度中断发生在后续迭代，不能证明模型最终一定不会修正。

看图工具确实返回了 0.39 / 0.44 / 0.88 倍等不同缩放的图片，故“把预览像素误当原图像素”是一个可疑机制；现有记录没有明确的换算过程，不能把它写成已证实根因。下一步应先按原图尺寸与物理尺寸校准各文字角色，再核对实际布局与同尺度局部预览，而非先改 DPI 或渲染器。

## 架构判断

### 第一优先：统一评估结果，保存中间成果，遇到硬额度停止

已用同一份旧候选在当前代码上复现：`checkAgentOutcome` 返回 `qualified`，实际 `render` 无图、75 条严重问题。这是当前接口语义的差异；审核与正式渲染并未漏拦截。

原因明确：`src/agent/candidates.ts:116` 的模板候选检查只执行 DSL 与 `prepareTemplates` 静态检查（`:150`）；`src/agent/review.ts:887` 才把渲染预览问题计入 `canApprove`，通过与应用都会重新检查（`:426`、`:479`）。MCP 的 `check_outcome` 复用了前者，因此“共用检查实现”还不足以等价于共用交付判据。

建议把指定请求的候选评估封装成一个模块，内部复用现有静态检查与渲染；`check_outcome`、审核、应用消费相同结果。对外至少分清：候选结构合法、内容是否完整、指定请求是否可渲染。已知引擎能力阻塞必须可被记录、保留草稿并结束本轮，不能降级成可正式交付。

这也解决提示词冲突：`agent/guide.md:32` 让模型报告阿拉伯文能力限制，而 `:42`、`:56` 和 `agent/tasks/template-design.md:18`、`:22` 又要求“没有严重问题”才交回或停止。阿拉伯文排版暂不实现的 M288 决定应保持；改的是失败结果如何结束和保存。

候选保存不应依赖“所有严重问题消失”。由宿主记录最近一次检查过的候选清单、文件哈希、问题与草稿路径，形成可恢复的中间记录；它和 Agent 正式提交的 `outcome.json`、用户批准分开，不能伪装成审核通过。模型完成每个区块后更新说明；能力阻塞可结束为“草稿可看、正式交付受阻”。运行层识别明确的周额度等终止条件，停止重试并给续跑命令，避免把硬额度问题交给模型自救。

验收同时覆盖：静态合法但渲染受阻、流中断可重试、硬额度不重复派发、进程被中止后仍能恢复候选。优先做这一项，因为本次已有成形模板却不能审核，其损失大于生成 JSON 的成本。

### 把信息覆盖与缺值依据变成可核对的交回材料

语法校验无法判断站码应不应该必填，也无法知道图上到站分钟数已经丢失。需要一份按图上业务内容列出的覆盖记录：归入字段、派生、出图参数、固定标签或待确认，并指出来源区域；若是派生，列出输入依赖与计算依据；固定业务内容必须有项目说明支持。

检查模块能确定性检查字段存在、路径有效、派生输入是否齐全、样例数据是否满足定义。图上语义仍需对照审核或独立事实断言；不能把 Agent 自报的区域当作正确性证据（沿用 M220）。本例的“15 个必填缺值仍进入下一步”与“累计分钟全空却没有待确认”应直接成为验收样例。

覆盖记录是解释和证据入口，不应把信息是否正确交给另一个同样缺证据的“自评通过”字段。将数据定义提取和最小样例数据校验组成一个闭环；缺必填值必须明确是定义过严、缺客户材料，还是待确认值。数据集再按覆盖记录检查是否漏了整个业务区块。

### 普通轮次也保存可复现清单

本次为对比补做了 `manifest.json`。`src/agent/run.ts` 保存图片、brief、工作区哈希与运行参数，但没有在普通轮次里保存源码提交、工具合同和全部资料哈希；评估路径已经有这些能力（`scripts/agent-eval/eval.ts:520`、`:550`、`:695`）。应提取共享的清单生成模块，让普通轮次和评估复用，并保存实际任务提示词。这样恢复与验收不必重新猜测当时的环境。

### 显示层优先补列表与缺省展示，减少无业务意义的派生变量

本次仅顶栏和方向横幅就生成了 32 个派生变量；为显示最多 4 个经由站，使用 `via1`–`via4`、`viaPrefix`、各项文本与分隔符，共 12 个派生变量。模板能通过检查，但 Agent 需要生成、维护大量取项和判空逻辑。证据为本次 `first-template-content.json`。

用“文本插槽的列表展示格式与缺省展示”作为优先方案，让列表连接、空值回退留在呈现模块；验收覆盖空列表、1/4 项、未知文本、缺值与分隔符。这样可减少提示词中的做法和模板中的重复逻辑。**不直接增加派生 `join` 运算**：ADR-0004 已决定拼接放文本插槽、不作为派生变量；若将来非文本属性也必须消费拼接结果，再明确重议该 ADR。此项排在正确性判据之后，先以本例测量减少的派生变量和生成成本。

## Coding agent 工作流建议

1. **以原失败案例关闭问题。** 票据 27 用 M402 的两次首检 0 验证提示词，票据正文也承认没有验证大模板。以后每张修复票同时列出代码合同断言和原场景实跑断言；全量测试通过不能替代后者。
2. **先保存事实基线，再做修复。** 对输入图、brief、资源、模型、源码、资料做哈希；旧失败与新运行分别保留，反馈修正另外计时计分。本次首次结果和经反馈结果分开报告，不以最后一轮合格覆盖早先的错误。
3. **实现与验收分开记录。** Coding agent 的交接必须写清失败复现命令、验收命令、预期行为和成果路径；下一位验收者从原输入复跑，不使用实现者修过的候选当初始输入。模型行为至少连续两次达线，且覆盖实际使用的模型。
4. **验收选信息量足的指标。** 数据用独立的值/缺省断言；模板同时看首检问题、预览问题、实际渲染、参数变体和视觉复核；预算看总轮次、输出 tokens、首次可恢复成果时点。首检 0 若只检查了空骨架，必须同时记录当时完成了哪些区块；否则指标可以改善，业务成果仍为空。本例还应记录普通站名与正文的字号、信息是否可辨认，避免靠把字缩小换取零溢出。
5. **保持只读 MCP 与文件成果。** 目前证据指向判据和信息归属失效，不足以证明需要“逐元素写入”工具。先把检查和交回语义做一致，再按 M290 的切换条件决定是否增加片段预检。
6. **把退出路径也做成正式交接。** 完成、能力受阻、额度受阻、运行中断分别记实；在昂贵模型调用之前检查可用配置，在执行中识别硬额度，在停止时保存最近检查结果与准确续跑命令。不要把“没有最终 outcome”误写成“没有任何可恢复工作”。

以上方案的取舍记录在 M294–M296、ADR-0021；排期与验收以票据 31–38 为准。
