# Tool Runner 执行器原型：对照记录

记录日期：2026-10-26，分支 `prototype/tool-runner-executor`（基于 `92583af`）。这是原型与对照观测，不是已采纳决定，也不计入正式评估门槛。背景见[平台化研究](../research/2026-10-26-platform-architecture.md)第 2 节。

**结论：修好图片尺寸之后，Tool Runner 执行器在 M230 的四个场景上各 2/2 达线，与同一构建上的 Claude Code 执行器（也是各 2/2）持平。四个场景合计：用时多 4%，输出 token 少 12%，缓存读少 6%。不依赖 Claude Code 跑这四类 Agent 任务可行。**

- 这次的四个场景分两次评估跑：M402 模板一次，另外三个场景一次，用的是同一构建，每个场景都连续两次达线。
- 正式门槛按惯例是一次评估跑满四个场景，所以这里不算正式门槛结论。

经过三组实验：

1. **首测**（`tr-proto-*`）：Tool Runner 0/2。
   - 第 2 次断在执行器缺陷上：`Read` 原样返回 3496×780 的示例图，对话累计超过 20 张图后被上游拒绝。
   - 第 1 次在「50 站 740」溢出，原因未查明。
2. **修复后复测**（`tr-proto2-*`）：`Read` 与 MCP 的图片进对话前缩到 2000 像素以内，每次请求前再核对。
   - 两边各 2 次都达线。
   - Tool Runner 两次都读了示例图并被缩小，对话里分别累计 25、27 张图，没再被拒。
3. **其余三个场景**（`tr-proto3-*`）：M402 数据定义、M402 模板辅助修改、366 转录。
   - 两边各 6/6 达线，评分几乎相同。
   - Tool Runner 在 8 个阶段轮次里有 7 次读了示例图，都被缩小；对话里最多 32 张图，没有被拒，也没有图被扣下。

首测第 1 次的溢出在复测中没有复现，推断是模型的随机性；每个场景 2 次的样本不足以排除执行器差异。

## 做了什么

- **执行器接缝**（[`src/agent/executor.ts`](../../src/agent/executor.ts)）：定义「执行一轮」的输入与结果。
  - 两种执行器都按 Claude Code stream-json 的形状写 `logs/stream.jsonl` 并交给 `onEvent`，所以用量、停滞控制、额度停止与评估指标都没有改。
  - `src/agent/run.ts` 只按 `executor` 选实现；Claude Code 执行器原样搬进 `claudeCodeExecutor()`，参数与环境不变。
- **Tool Runner 执行器**（[`src/agent/tool-runner-executor.ts`](../../src/agent/tool-runner-executor.ts)）：用 `@anthropic-ai/sdk` 0.133.0 的 `client.beta.messages.toolRunner`。
  - 模型请求只发往本轮本机代理，只带本轮令牌，与 Claude Code 执行器相同（M321）。
  - 领域工具经同一个受管 MCP（stdio 桥、宿主检查点）调用，工具名仍是 `mcp__rw__<名称>`。
  - `Read`、`Write`、`Edit`、`Glob` 在宿主内实现，限定在工作目录，输入字段沿用 Claude Code 的写法。
  - 请求参数对齐 Claude Code 对同一模型的实际请求：`max_tokens` 128000、自适应思考、`effort` medium。这些值是用本机协议夹具抓取 Claude Code 2.1.296 的请求得到的。
- **图片预算**（[`src/agent/image-budget.ts`](../../src/agent/image-budget.ts)，复测前加的）：
  - `Read` 与 MCP 返回的图片进入对话前，长边缩到 2000 以内；base64 超 5 MB 时继续缩小。`Read` 同时说明原图与输出尺寸。
  - 图片到 100 张或请求体到 30 MB 时，改为一句文字说明，不中断本轮。
  - 每次请求前，按将要发出的完整请求体核对图片数、每张图是否经过核对、尺寸与体积；不过就停止本轮并写明原因。
  - 上限取自 Claude API 视觉文档「Request limits」（2026-10-26 查阅）：一次请求超过 20 张图时每张不超过 2000 像素；单张 base64 在 Bedrock 上不超过 5 MB；上下文 200k 的模型每次最多 100 张；请求体不超过 32 MB。上游渠道不明，所以都取较严的值。
- **入口**：`renderweave agent run --executor tool-runner`；评估透传 `--executor`。只有不是缺省值时才写进轮次记录与实验身份，所以已有记录与身份不变。
- **离线测试**（[`test/agent-tool-runner.test.ts`](../../test/agent-tool-runner.test.ts)）：经命令行与本机模型协议夹具验收四件事。
  - 工作目录外的读写被拒绝，`check_outcome` 后交回，审核与应用照常。
  - 3500×800 的图读 21 次，请求里 21 张都是 2000×457，并附原图尺寸说明。
  - 一轮读 101 次图，请求里只有 100 张图，第 101 次收到文字说明。
  - 用满轮数时以 `error_max_turns` 结束。

`tr-proto-cc` 与 `tr-proto-tr`，`--repeat 2`，第 1、2 次分两段跑，每段两边同时派发。

**口径说明**：
- **CC、TR**：分别指 Claude Code 执行器和 Tool Runner 执行器。
- **模型请求数**：两边 `turns` 的口径不同（CC 记 68、74，TR 每次请求算一轮），表里改用两边都能数的不同 assistant 消息数。
- **墙钟**：首测时另一会话的评估同时在跑（16 个逻辑核，另有约 15 个评估进程），两边处境相同，绝对值不能代表空闲机器上的表现。
- **TR 第 2 次**：中途中断，用量和耗时不能拿来比。

### 第 2 次的根因

已验证：
- 结束消息是上游 400：`At least one of the image dimensions exceed max allowed size for many-image requests: 3000 pixels`。
- 轮次里的示例图是 3496×780 的 PNG；模型用 `Read` 读了它，当时的 `Read` 原样返回整张图。
- 对话里累计到第 21 张图后，下一次请求被拒。这一轮断在压测中途，最后几次 `render_draft` 正在试「两站」「五十站」，没能调用 `check_outcome`。
- CC 两次都没有用 `Read` 读示例图，所以没碰到这个限制。

推断：「2 站」的 `render.sizeOutOfRange` 是还没修完就被打断留下的。

后来已验证：Claude Code 的 `Read` 会把大图缩到长边 1999 像素（见「其余三个场景」）。原型当时没有这一步。

### 第 1 次的推断

TR 第 1 次自检明显少（`check_templates` 1 次，CC 两次是 6、5 次），没有发现「50 站 740」的溢出。原先推断差异来自系统提示词：Claude Code 自带约 6,500 字符、要求反复验证的提示词，原型只给了一段很短的说明。

这条推断后来变弱了：
- TR 第 2 次自检并不少（`check_templates` 7 次、`Edit` 20 次）。
- 复测中 TR 用同一个提示词，两次都 10/10。

更可能是模型的随机性。

## 已知差异与限制

- **系统提示词**：由原型自己给出（`SYSTEM_PROMPT`），不带 Claude Code 的提示词。四个场景各 2 次，质量持平；更多领域与语言（如模板设计评估集的 12 例、英文样例）还没测。
- **没有上下文管理**：没有压缩，也没有超长工具结果转存。
  - 工具结果仍由 MCP 服务限制在 40,000 字符以内（票据 22）。
  - M402 模板复测中，TR 单次请求输入最多 160,791 token（含缓存），离上下文上限很远。
- **用满轮数时工具仍会执行**：Tool Runner 会执行最后一轮的工具调用，之后才停，执行器按实际情况记录。Claude Code 在这一点上的行为没查。
- **OpenCode Go 要求会话头**：缺 `x-opencode-session` 时返回 400 `MissingSessionID`，执行器每轮生成一个。这是实测发现的。
- **模型会调用不存在的工具**：两种执行器下都出现过（如 `View`、`View_image_placeholder`、不带前缀的 `view_image`），是模型自己的行为。
  - Tool Runner 按"没有这个工具"回给模型；Claude Code 怎么回没查。
  - 评估的 `toolErrors` 只数 MCP 调用日志，没有计入这些调用。
- **依赖变大**：`node_modules` 从 137 MB 增至 156 MB。
  - 候选冻结会复制整个 `node_modules`，「计划绑定同一候选后实际派发」这个用例在 120 秒处超时；main 上同一用例通过。
- **执行器身份**：评估身份仍检查 `claude --version`，Tool Runner 的轮次也要求本机装有 Claude Code。正式化时要按执行器分开。
- **共用检出的风险**：在评估正在运行的检出里构建或装依赖，会改变 `dist/`、`package-lock.json` 或评估脚本的哈希，正在跑的评估会在下一次派发前停止。本原型因此改在独立 worktree 里进行。

## 测试

- 类型检查：`npx tsc --noEmit` 通过。
- `test/agent-tool-runner.test.ts` 的 4 个用例：通过。
- `npx vitest run test/agent --maxWorkers=2`（加图片预算之前跑的）：376 通过、6 失败，逐个核对如下。
  - `agent-orders` 的断言失败：单独重跑通过。
  - 两个超时：机器负载所致，单独重跑通过。
  - `agent-candidate-freeze` 的 3 个失败：2 个在 main 上同样失败（Windows 建符号链接 EPERM，以及冻结用例超过 60 秒）；1 个是上面「依赖变大」那条。
- 图片预算只改了 Tool Runner 执行器的文件，之后没有重跑全量 agent 测试。
