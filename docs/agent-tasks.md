# 业务 Agent 任务

`renderweave agent run` 发起一轮业务 Agent 任务：在独占的轮次目录里组装资料，按 [ADR-0015](adr/0015-agent-runs-as-headless-claude-code-via-read-only-mcp.md) 启动一次 Claude Code 无头运行。

Agent 只连本仓库的 [MCP 只读工具服务](mcp.md)。结束后，RenderWeave 先校验 Agent 交回的成果结构，再用引擎校验候选文件。代建工程师用 `renderweave agent review` 在本地审核页审核成果，审核通过后用 `renderweave agent apply` 写入工作区。决定记录见：

- M226：发起与成果；
- M227：审核与应用；
- M228：数据集提取与模板辅助设计；
- M229：带反馈的下一轮与模板辅助修改。

四种任务都已实现：**数据定义提取**、**数据集提取**、**模板辅助设计**、**模板辅助修改**，以及它们的审核、应用与带反馈的下一轮。

流程（M43 的任务顺序）：

```text
数据定义提取 → 审核 → 应用（发布为静态数据定义）
  → 数据集提取 → 审核 → 应用（保存数据集）
  → 模板辅助设计 → 审核 → 应用（保存模板）→ renderweave deliver 正式出图
  → 模板辅助修改 → 审核 → 应用（工作副本替换已保存的模板）→ renderweave deliver

任何一轮审核不通过（或成果结构不合格）→ 带反馈的下一轮（--from、--feedback）→ 审核 → …
```

## 发起一轮

```bash
renderweave agent run --task 数据定义提取 --sample <示例图> --brief <项目说明.md> --resources <资源仓库> --out <新轮次目录> [--domain route-sign] [--workspace <工作区>]
renderweave agent run --task 数据集提取 --definition <名称[@版本]> --workspace <工作区> [--request <出图请求.json>] …
renderweave agent run --task 模板辅助设计 --dataset <数据集ID> --request <出图请求.json> --workspace <工作区> …
renderweave agent run --task 模板辅助修改 --request <出图请求.json> --requirement <修改要求.md> --workspace <工作区> [--dataset <数据集ID>] …
renderweave agent run --from <上一轮目录> --feedback <反馈.md> --out <新轮次目录> [运行参数]
```

| 选项 | 含义 |
|---|---|
| `--task` | 任务类型：`数据定义提取`、`数据集提取`、`模板辅助设计`、`模板辅助修改`，也可写英文标识 `definition-extraction`、`dataset-extraction`、`template-design`、`template-revision` |
| `--sample` | 示例图，PNG、JPEG 或 WebP，按文件头判断格式，不看扩展名 |
| `--brief` | 项目说明：业务、尺寸、目标范围、客户说明。只写这一单的事实 |
| `--resources` | 资源仓库目录，Agent 经工具查看可引用的图片与字体；审核时重新渲染预览也用它 |
| `--out` | 新轮次目录，必须不存在或为空 |
| `--domain` | 可选，领域约定包，取 `agent/domains/<领域>.md`，目前有 `route-sign` |
| `--workspace` | 工作区目录，复制为本轮的只读快照。数据定义提取可选，其余三种任务必须给 |
| `--definition` | 数据集提取所基于的已发布数据定义：`名称` 或 `名称@版本`，只写名称时取最新版本 |
| `--dataset` | 模板辅助设计所基于的已保存数据集 id，数据定义取它选定的那一份；模板辅助修改可用它代替出图请求中的数据集 |
| `--request` | 示例图对应的出图请求（主模板名、对外参数与输出尺寸）。模板辅助设计与模板辅助修改必须给；数据集提取可选，给了就用工作区已有的模板预览候选数据集 |
| `--requirement` | 模板辅助修改的修改要求（Markdown），见[模板辅助修改](#模板辅助修改) |
| `--from`、`--feedback` | 带反馈发起下一轮，见[下一轮](#下一轮) |
| `--key-env` | 可选，key 所在的环境变量名，缺省 `QWEN_TOKEN_PLAN_API_KEY` |
| `--model`、`--small-model`、`--endpoint` | 可选，缺省为千问 token plan 的 qwen3.8-max、qwen3.7-plus 与对应的兼容端点 |
| `--max-turns` | 可选，轮数上限，缺省见下表 |
| `--claude` | 可选，Claude Code 可执行文件，缺省为 PATH 上的 `claude` |

**三种任务**：

| 任务 | 前提（M43） | 成果 | DSL 参考 | MCP 工具 | 轮数上限 |
|---|---|---|---|---|---|
| 数据定义提取 | 无 | 数据定义 | 数据定义与数据集 | `list_documents`、`read_document`、`list_resources`、`check_definitions`、`check_dataset`、`view_image`、`dsl_reference` | 40 |
| 数据集提取 | 已发布的数据定义 | 一份数据集 | 数据定义与数据集 | `list_documents`、`read_document`、`list_resources`、`check_dataset`、`view_image`、`dsl_reference`、`render_draft` | 40 |
| 模板辅助设计 | 已保存的数据集 | 主模板与被调模板 | 模板 | `list_documents`、`read_document`、`list_resources`、`check_templates`、`render_draft`、`inspect_layout`、`view_image`、`dsl_reference` | 80 |
| 模板辅助修改 | 已保存的模板与数据集 | 工作副本与新建的被调模板 | 模板 | 同模板辅助设计 | 80 |

**任务顺序**：只给示例图、没有指定数据定义时，命令提示先做数据定义提取；模板辅助设计没有 `--dataset` 时，提示先做数据集提取并应用。所选的数据定义或数据集不在工作区中时，列出可用的。

**出图请求**：命令先规范化，再存进轮次目录的 `request.json`（审核时用），并复制给 Agent 作 `docs/request.json`：

- 模板辅助设计：数据集固定为 `{"id": <--dataset>}`；请求的主模板名就是 Agent 要写的主模板。
- 数据集提取：去掉数据集，预览时换成候选；主模板必须已在工作区中，且基准是所选数据定义。
- 模板辅助修改：主模板必须已在工作区中，它就是要修改的模板；数据集取 `--dataset` 或请求中的 `{"id": …}`，必须是已保存的数据集。

**退出码**：

| 退出码 | 含义 |
|---|---|
| 0 | 成果合格 |
| 1 | 成果不合格，问题清单在 `check.json` 并写到标准错误流。是否带着问题重跑由人决定，不自动重试（M48） |
| 2 | 用法错误，或输入无法读取，或任务顺序不对。此时不创建轮次目录 |

**标准输出**是一段 JSON 摘要：轮次目录、第几轮与上一轮、结论、候选（数据定义的发布版本，模板辅助修改的改动情况与改动处数）、待确认项数、用时与轮数。

## 模板辅助修改

输入是已保存的模板与修改要求，成果是工作副本（M49）。

- **可以改的范围**：出图请求的主模板，以及它直接、间接调用的已保存模板（调用树）。命令把它们原样复制进 `agent/candidates/`，文件名与工作区相同，Agent 直接在上面修改；需要新的被调模板时另建文件。调用树以外的已保存模板不能改。
- **基准**（M51）：`round.json` 的 `inputs.templates` 记下调用树中每个模板的文件名与内容 SHA-256，轮次成果中每个工作副本的 `revises` 指向它所基于的那一份。
- **修改要求**：Markdown，可以写元素路径（从模板名开始，用 / 分隔，不带循环序号）。反引号里以调用树中模板名开头的元素路径必须找得到，否则报用法错误，例如 `` `站点格/站名框/地标` ``。只在第 1 轮核对：下一轮沿用修改要求时，上一轮可能已经把这些元素改名或移走并应用了。修改要求存进轮次目录的 `requirement.md`，并给 Agent 作 `docs/requirement.md`；冲突时修改要求优先于项目说明。
- **成果**：`candidates` 只列改过的模板与新建的模板。与已保存模板同名的候选就是它的工作副本，校验与预览时代替已保存的模板（M50）。
- **结构化差异**：RenderWeave 比对工作副本与已保存的模板，不靠 Agent 自述。元素按元素路径配对，比对自身的属性（子元素各自比对），子元素换了先后次序单独列出；模板层比对画板以外的键，参数、派生变量与检查项按名称逐项比对。每处改动给出位置、属性与修改前后的值。差异写在 `check.json` 每个候选的 `revision` 中（`modified`、`unchanged` 或 `added`），审核视图按审核后的工作副本重新计算。与已保存内容相同的工作副本只记提示，应用时不写入。公开入口 `diffTemplate` 给出同样的差异。

## 下一轮

```bash
renderweave agent run --from <上一轮目录> --feedback <反馈.md> --out <新轮次目录> [--model …] [--key-env …] [--max-turns …]
```

下一轮的输入是素材、上一轮成果（含审核时的修改）与反馈（M58）。每轮一个独立目录，状态由 RenderWeave 保存。

- **沿用**：任务、示例图、项目说明、领域约定、所基于的数据定义与数据集、出图请求与修改要求都沿用上一轮，命令行不能再给；要换输入就重新发起第 1 轮。工作区与资源仓库沿用上一轮的来源，工作区重新取快照，所以两轮之间别人保存的内容会进入下一轮。运行参数（模型、轮数上限等）照常给，缺省值不继承。
- **上一轮成果**：按上一轮的 `review.json` 作用审核时的修改，规则与审核页、应用相同；整份标为空的候选不再给。审核通过、不通过或还没审核的轮次都可以作为上一轮。上一轮结构不合格、没有轮次成果时，给 Agent 当时交回的 `candidates/` 下的文件与问题清单。上一轮的审核结果不合格或相互矛盾时拒绝发起。
- **交给 Agent 的内容**：
  - `candidates/` 放好上一轮成果，作为本轮的起点；
  - `previous/` 是上一轮的原样记录：`candidates/`（含审核时的修改）、`outcome.json`、`review.json`、`check.json`（有哪些给哪些）；
  - `docs/feedback.md` 是反馈，也存进轮次目录的 `feedback.md`；
  - 提示词在任务提示词之后接上 `agent/tasks/next-round.md`：第几轮、各文件的用途、候选从哪里开始，以及反馈优先于其余资料。
- **模板辅助修改的下一轮**：已保存的模板自上一轮之后没变时，候选从上一轮的工作副本继续；变了，候选从最新保存的内容开始，`inputs.previous.basisChanged` 为 `true`。变了有两种情况，提示词分别说明：上一轮已经应用，最新内容就含上一轮的修改；别人保存过（例如应用时发现冲突、选择重做），上一轮的工作副本只放在 `previous/` 作参考。
- **轮次链**：`round.json` 的 `inputs.previous` 记录上一轮的目录、轮次、成果与审核结果的 SHA-256 及审核状态，`round` 为上一轮加 1。审核视图的 `round.chain` 沿它追溯到第 1 轮，列出每轮的结论、审核状态与是否应用；某一轮的目录读不到时，链在那里断开并标出。公开入口 `readRoundChain` 给出同样的链。

## 隔离

- **环境**：子进程环境从空白开始，只放系统必需变量与模型配置，不继承宿主的 `CLAUDE_*`、`ANTHROPIC_*` 变量与登录凭据。
- **配置目录**：独立，放在轮次目录的 `logs/claude-config/`。
- **key**：只从环境变量读取，只在内存中传给子进程。轮次目录的任何文件里都没有 key，`round.json` 只记录变量名。
- **权限**：
  - 以 `--restricted` 运行，没有执行代码的工具，文件工具限于 Agent 工作目录；
  - `--strict-mcp-config` 只连 `renderweave mcp`，工具按任务开放（见上表）。

## 轮次目录

| 路径 | 内容 |
|---|---|
| `agent/` | Agent 工作目录，即 MCP 服务的 `--root` |
| `agent/sample.<格式>` | 示例图 |
| `agent/docs/` | `brief.md`（项目说明）、`guide.md`（通用做法）、`domain-<领域>.md`（领域约定，如有）、`dsl-reference.md`（DSL 参考）、`outcome.md`（成果格式）、`request.json`（出图请求，如有）、`requirement.md`（修改要求，模板辅助修改）、`feedback.md`（反馈，下一轮） |
| `agent/candidates/` | Agent 写的候选文件；模板辅助修改与下一轮由命令预先放好起点 |
| `agent/previous/` | 下一轮才有：上一轮的原样记录 |
| `agent/scratch/` | Agent 的自查草稿，不是成果 |
| `agent/outcome.json` | Agent 交回的成果 |
| `snapshot/` | 工作区快照，MCP 服务启动时读入 |
| `logs/` | `mcp.json`、`stream.jsonl`（Claude Code 流式输出）、`stderr.txt`、`tools.jsonl`（工具调用日志）、`claude-config/` |
| `request.json` | 规范化后的出图请求，审核时按它重新渲染预览；Agent 改不到 |
| `requirement.md`、`feedback.md` | 修改要求与反馈的副本，审核页显示；下一轮沿用修改要求 |
| `round.json` | 轮次记录：输入（含所基于的数据定义、数据集、出图请求、资源仓库、模板辅助修改的基准与修改要求、上一轮与反馈）、运行参数、用量与结论，无论成果是否合格都写出 |
| `check.json` | 校验结果：结构问题与每个候选的问题 |
| `outcome.json` | 轮次成果，结构合格时才写出 |
| `candidates/` | 候选文件的副本，之后审核与应用都读这里 |
| `previews/` | 审核页的预览图与问题清单，按输入的哈希缓存 |
| `review.json` | 审核结果，由审核页写出（见[审核](#审核)） |
| `applied.json` | 应用记录，应用成功后写出；有它就不能再应用（见[应用](#应用)） |

提示词取 `agent/tasks/<任务>.md`，只写三层资料的优先级与做事步骤，不含具体业务；所选的数据定义、数据集、主模板名与可修改的模板由命令填入。下一轮另接 `agent/tasks/next-round.md`。

## 成果

### Agent 交回的 outcome.json

格式写在 [agent/reference/outcome.md](../agent/reference/outcome.md)，它同时是交给 Agent 的资料。要点如下：

- `candidates`：候选文件列表，必须在 `candidates/` 下，种类符合任务（M43）。数据定义提取时，按示例图写的数据集只能作为 `scratch/` 中的自查草稿。
- `locations`：可选，候选中的位置在示例图上对应哪一部分，供审核人对照。
  - `file` 指向一个候选，`path` 是位置（省略表示整份文件）；
  - `where` 是文字描述；
  - `region` 可选，是示例图上的像素区域 `{x, y, width, height}`，写法与 `view_image` 相同。

  这是 Agent 的自述，不是识别证据（M220）。审核页的元素清单把它挂到最深的、包含它的元素上，例如穿进被调模板的位置挂到循环或调用元素那一行。
- `pending`：待确认项。
  - `file` 指向一个候选，`path` 是位置；
  - `candidate` 是候选值，可以没有。数据集中是该位置的值，草稿预览与"采纳候选"都用它；数据定义与模板中是给审核人的建议；
  - `reason` 是原因，取 M44 的四类之一：`unreadable`（看不清）、`inferred`（推测）、`conflicting`（来源冲突）、`requiredMissing`（必填未提供）；
  - `note` 是说明。
- `notes`：给审核人的说明。

**位置的写法**：

| 候选种类 | `path` | 例子 |
|---|---|---|
| 数据定义 | 字段名 | `role` |
| 数据集 | `data` 中的字段路径，列表序号从 1 开始，与问题清单一致；最后一段可以是还没有值的字段 | `sessions[2].title` |
| 模板 | 元素路径，不带循环序号；可以从模板名开始，也可以省略模板名，审核时统一补上（M101）。被调模板里的元素，`file` 写被调模板的文件 | `姓名区/姓名`、`胸牌/姓名区/姓名` |

### 校验

1. **结构**：先查以下几项，任一不合格都报 `outcome.invalid`：
   - `outcome.json` 是否可读、是否符合格式；
   - 候选文件是否在 `candidates/` 下、可读、种类对；
   - 数据定义名称是否重复；
   - 待确认项是否指向候选，位置是否存在；
   - 图上位置只给审核人参考：指向不对或位置找不到时只记提示，不影响结论；
   - 模板辅助设计时，出图请求的主模板是否在候选中；
   - 模板辅助修改时，与已保存模板相同的工作副本记提示。
2. **引擎**：
   - **数据定义**：按依赖顺序在内存中发布，引用其他候选的定义放在后面，版本号接在工作区快照之后。
   - **数据集**：先按 `schemas/dataset.schema.json` 做 Schema 前置校验；再查 `dataset.id`，必须有、不与工作区重复，还要查是否选定本轮的数据定义；最后按编译产物校验数据。校验前，先把待确认项的候选值写到对应位置。
   - **模板**：先按 `schemas/template.schema.json` 做 Schema 前置校验；再把全部候选作为工作副本做静态检查（M49、M50），同名的代替已保存的模板。模板辅助设计只新建模板，名称不能与工作区已有的模板重复；模板辅助修改只能改主模板调用树中的已保存模板，新建的模板同样不能与工作区重名。

   Schema 不通过时只报 Schema 的问题，不再做引擎校验。
3. **结论**：结构合格，且候选没有严重问题时为"合格"。数据集中落在待确认位置上的问题，如必填未提供，记在候选的 `deferred` 里，留给审核处理，不计入结论（M46）。

### 轮次成果 outcome.json

结构合格时写出，格式标识 `renderweave-outcome/1`：

| 键 | 内容 |
|---|---|
| `task`、`round` | 任务类型与轮次，首轮为 1，下一轮为上一轮加 1 |
| `inputs` | 示例图的 SHA-256、工作区快照指纹、上一轮（目录、轮次、成果与审核结果的 SHA-256，首轮为 `null`）、反馈的 SHA-256（下一轮）。应用前用指纹判断工作区是否已变（M51） |
| `candidates` | 路径、种类、名称（数据集为 id）、SHA-256；数据定义另有在内存中发布成的名称与版本；模板辅助修改的工作副本另有 `revises`：所基于的工作区文件名与内容 SHA-256 |
| `locations`、`pending`、`notes` | 来自 Agent 交回的内容；没交 `locations` 时为空列表 |
| `usage` | 用时、轮数、输入与输出 token、缓存 token、实际服务的模型、Claude Code 版本、结束方式（如 `success`、`error_max_turns`） |

工作区指纹是快照中各 JSON 文件的文件名与内容哈希，按文件名排序后再整体取 SHA-256。

## 审核

```bash
renderweave agent review <轮次目录> [--port <端口>] [--no-open]
```

命令在 `127.0.0.1` 上启动审核页，打开默认浏览器，并把地址打印到标准输出；按 Ctrl+C 结束。有 `outcome.json` 的轮次都能审核，成果校验不合格的也可以，处理后没有严重问题才能通过。

**页面内容**：

| 区域 | 内容 |
|---|---|
| 示例图与预览 | 有出图请求时，示例图与 RenderWeave 重新渲染的预览上下对照，缩放与滚动可以联动；模板辅助修改时是示例图、修改后、修改前三张。各图都能适应窗口、按 100%、200%、400% 显示，单击放大、Shift+单击缩小；点"定位"在示例图上框出位置 |
| 审核结论 | 待确认项处理进度、"其余内容已整体确认"、备注或理由、通过与不通过、撤回结论，以及还不能通过的原因 |
| 轮次 | 多轮或模板辅助修改时才有：轮次链（每轮的结论、审核状态、是否应用与目录）、修改要求、上一轮审核后的反馈 |
| 预览 | 出图请求、像素尺寸与 DPI、预览的问题清单；模板辅助修改时修改前后各一份 |
| 待确认项 | 每项一张卡片：原因、位置、Agent 的说明、候选值、候选文件中的当前写法，以及三种处理方式 |
| 候选 | 数据定义：字段清单（名称、显示名称、类型、约束、图上位置、说明、相关的待确认项）与编译产物摘要。数据集：选定的数据定义与逐个值的清单（字段路径、值、图上位置、相关的待确认项）。模板：基准、对外参数与元素清单（元素路径、类型、图上位置、相关的待确认项）；模板辅助修改另有相对已保存模板的改动表（位置、属性、修改前、修改后）。都附完整文档与引擎问题 |
| Agent 的说明 | `notes`，以及用时、轮数、输出 token 与模型 |

Agent 写的说明与候选内容一律按纯文本显示，不当作 HTML。

**预览**（M52）：

- 由 RenderWeave 按轮次目录的 `request.json` 重新渲染，用草稿模式（问题处画框、缺失处占位），不用 Agent 自己的图；
- 模板辅助设计：用审核后的候选模板，代替或加入快照中的模板，数据集是已保存的那一份；预览的严重问题阻止通过；
- 数据集提取：用快照中已保存的模板，数据集是审核后的候选，问题只作参考，因为模板不是本轮的成果；
- 模板辅助修改：修改后的预览同模板辅助设计，审核后的工作副本代替同名的已保存模板（M50），严重问题阻止通过；修改前的预览只用快照中已保存的模板，问题只作参考；
- DPI 按示例图的像素宽度折算，不低于 50，不超过 300，最长边不超过 4000 像素，两图因此可以按同样的显示宽度对照；
- 每次审核操作后按审核结果重新渲染；同样的输入（请求、候选与渲染器构建）直接取 `previews/` 中的缓存。

**处理待确认项**（M47）：

| 处理方式 | `action` | 效果 |
|---|---|---|
| 采纳候选 | `adopt` | 数据定义与模板：保留候选文件中该位置的写法。数据集：把候选值写到该位置，没有候选值时保留文件中的值 |
| 改值 | `edit` | 用审核人写的值替换该位置：数据定义中是整个字段，模板中是整个元素，数据集中是该位置的值；没有 `path` 时是整份文件 |
| 标为空 | `empty` | 删去该位置：删字段、删元素或删值；没有 `path` 时不写入这份候选 |

数据集中还没处理的待确认项，在预览与校验中先用候选值（M46）。待确认项全部处理、其余内容整体确认、引擎校验（与模板辅助设计的预览）没有严重问题，三者都满足才能通过，所以待确认项没处理完时不会写入数据集。以下情况也会报出：

- 两个待确认项指向同一位置，但处理结果不同；
- 两个处理结果的位置相互包含，如 `sessions[2]` 与 `sessions[2].title`；
- 同一份候选既整份处理、又处理了其中的位置。

给出结论（通过或不通过）后，要先撤回结论才能再改；应用后不能再改。

**review.json**（`renderweave-review/1`）：

| 键 | 内容 |
|---|---|
| `outcomeSha256` | 所审核的 `outcome.json` 的 SHA-256。成果变了，审核结果作废 |
| `status` | `inProgress`（审核中）、`approved`（通过）、`rejected`（不通过） |
| `decisions` | 每项含 `item`（待确认项序号，从 1 开始）、`file`、`path`、`action`；改值时另有 `value` |
| `restConfirmed` | 其余内容已整体确认 |
| `comment` | 不通过的理由，或通过时的备注 |
| `updatedAt`、`decidedAt` | 最后修改时间与给出结论的时间 |

- 每次操作立即整份替换 `review.json`，所以关闭页面后重新打开，可以接着审核。
- `review.json` 在 Agent 工作目录之外，Agent 写不到。
- 公开入口 `readReview`、`changeReview` 读写同一份文件，页面只是它们之上的一层。

**本地服务的边界**：

- 只绑定 `127.0.0.1`，只服务一个轮次目录；
- `Host` 必须是本机地址加本服务端口，防止 DNS 重绑定；
- 写操作必须是 `application/json`，`Origin` 若有必须是本服务。其他网页即使知道端口，也改不了审核结果；
- 预览图只按 64 位十六进制哈希的文件名提供。

## 应用

```bash
renderweave agent apply <轮次目录> [--workspace <目录>] [--overwrite]
```

把审核通过的一轮写入工作区，审核时改过的内容以审核结果为准：

| 种类 | 写入 | 文件名 |
|---|---|---|
| 数据定义 | 经发布入口发布为下一个版本（M18） | `schema-<名称>-v<版本>.json` 与 `compiled-<名称>-v<版本>.schema.json`，规则与 `renderweave publish` 相同 |
| 数据集 | 作为新数据集保存 | `dataset-<名称>.json` |
| 模板 | 作为新模板保存（M49 的"应用即保存"） | `template-<名称>.json` |
| 模板的工作副本（模板辅助修改） | 整份替换当前保存这份模板的文件；与已保存内容相同的不写，记在 `unchanged` 里 | 沿用工作区中的文件名 |

名称取候选文件名，去掉 `schema-`、`dataset-`、`template-` 前缀与 `-v<版本>` 后缀。应用后即可用 `renderweave deliver` 正式出图。

- **工作区**：缺省为发起本轮时的 `--workspace`；发起时没有给工作区的，必须用 `--workspace` 指定。
- **拒绝**：以下情况拒绝应用，退出码为 1，工作区一字不变：
  - 没有 `review.json`；
  - 审核还在进行，或审核未通过；
  - 候选或成果自生成后被改动；
  - 本轮已经应用过（有 `applied.json`）；
  - 工作区指纹与成果记录的不同。

  工作区指纹不同时，标准错误流列出差异：同名数据定义在快照之后发布的新版本、新增、删除与修改的文件。模板辅助修改要改的模板已被他人保存时（当前文件的内容或文件名与基准不同，或模板已删去），另列出他人自基准以来的改动（`drift.templates`，写法同结构化差异）。之后由人选择（M51）：
  - **覆盖**：加 `--overwrite`，按当前工作区写入；模板的工作副本替换最新保存的内容，他人的改动随之丢失，记在应用记录的差异里；
  - **重做**：基于当前工作区重新发起一轮；模板辅助修改用 `--from <本轮> --feedback <反馈>`，候选从最新保存的内容开始。
- **覆盖时的数据定义**：版本号可能后移。例如别人已经发布了场次 v1，本轮的场次就发布为 v2。候选之间的引用随之改到新版本；引用工作区中已有定义的不变。
- **覆盖时的数据集与模板**：先在当前工作区上重新校验。工作区已有同 id 的数据集或同名模板时，即使覆盖也拒绝，不替换别人保存的内容；修改已保存的模板用模板辅助修改。
- **原子性**：全部内容先在当前工作区上校验或在内存中发布，全部成功才写文件。先排他创建全部新文件（已存在就失败，不覆盖），再逐个替换模板的工作副本（先写临时文件再改名），最后写入新文件的内容；任何一步失败，或应用记录写不出，就撤回本次写入：删去新建的文件，替换过的文件恢复原内容。
- **应用记录** `applied.json`（`renderweave-applied/1`）：
  - 应用时间、工作区、是否覆盖；
  - 三个指纹：成果所基于的、应用前、应用后；
  - 写入的种类、名称、版本（仅数据定义）与文件，替换已保存模板的带 `replaced`；没有写入的工作副本列在 `unchanged`；
  - 覆盖时另有差异。

**退出码**：0 已应用；1 拒绝或失败；2 用法错误或工作区无法读取。标准输出是一段 JSON：工作区、是否覆盖、写入的名称、版本与文件。

`test/agent-review.test.ts` 经 `readReview`、`changeReview`、`applyAgentRound` 与命令行，覆盖数据定义的审核与应用：

- **审核视图**：字段清单、图上位置、编译产物摘要；
- **审核操作**：逐项处理与整体确认；关闭后重开；撤回结论；
- **拒绝的情形**：不合规的操作、改值后不合格、同一位置处理不一致、整份标为空、审核结果与成果对不上、候选被改动；
- **应用**：
  - 未审核、审核中与未通过时不能应用；
  - 通过后发布为新版本，审核改动以审核结果为准；
  - 不能重复应用；
  - 工作区变化时给出差异；覆盖后候选间的引用改到新版本；
  - 写入失败时撤回；
- **审核页服务**：页面、示例图、读写审核结果；拒绝跨站与非本机 Host 的请求；Ctrl+C 后结束。

`test/agent-dataset-template.test.ts` 覆盖数据集提取与模板辅助设计：

- **发起**：任务顺序与 12 种输入错误；轮次记录、出图请求的规范化、提示词、DSL 参考与开放的工具。
- **成果校验**：
  - Schema 前置校验；
  - 数据集 id 重复、选定的数据定义不对、约束不满足；
  - 待确认位置上的问题留给审核；
  - 主模板不在候选中、元素路径不存在、模板与工作区重名、被调模板不存在；
  - 元素路径可以省略模板名；穿进被调模板的图上位置只记提示，在元素清单中挂到调用元素那一行。
- **审核**：
  - 数据清单与元素清单；
  - 预览与按同样输入直接渲染的结果逐字节一致，且不是 Agent 草稿目录里的图；
  - 处理待确认项后，预览随之更新；
  - 数据集的待确认项没处理完时，不能通过，也不能应用（M46）；
  - 模板辅助设计时，预览的严重问题阻止通过。
- **应用与出图**：写入数据集或模板后，经 `deliverBatch` 正式出图，产生出图记录；工作区出现同名模板时，即使覆盖也拒绝。
- **审核页服务**：提供预览图，拒绝不合规的预览图文件名。

`test/agent-rounds.test.ts` 覆盖带反馈的下一轮与模板辅助修改：

- **下一轮**：拿到素材、上一轮成果（含审核时的修改）、原样记录与反馈；工作区重新取快照；轮次链追到第 1 轮，目录不见时断开；上一轮结构不合格时拿到当时的文件与问题清单；不能再给沿用的输入、必须带反馈、上一轮的审核结果不合格时拒绝。
- **模板辅助修改的发起**：9 种输入错误（含修改要求中找不到的元素路径）；调用树中的已保存模板预置为工作副本，记录基准；提示词与工具。
- **成果**：结构化差异；没改的只记提示；新建模板；调用树以外的模板不能改；`diffTemplate` 的元素配对、换序与按名称比对。
- **审核**：修改前后的预览与直接渲染逐字节一致；审核时改动工作副本，差异与修改后的预览随之更新。
- **应用**：工作副本替换已保存的模板，没改的不写，之后正式出图；应用后的下一轮从最新保存的内容开始；修改要求只在第 1 轮核对元素路径，上一轮改名并应用后照样沿用；模板已被他人保存时列出他人的改动、拒绝，重做时候选从最新内容开始，覆盖时替换；只有无关文件变化时不列模板冲突；新文件名被占用时撤回；Windows 上第二个替换失败时恢复第一个。
