# 第四阶段验收：出图服务第一版（v1.0）

结论：第四阶段验收通过，可以结束。出图服务第一版在本机 Docker Compose 上从空环境走完了 PRD 的完成标准。

- **能力**：A01–A12 通过。
  - 完成标准的全流程由验收脚本从空环境走完：平台管理员开通、代建推送、操作员在控制台用表单与 Excel 出图、导出与离线重放、用量与超额拒绝、客户开发者经开放 API 交付并收到签名的 webhook（见「完成标准的全流程」）。
  - 真人走查由用户本人做，从登录到导出记录动手约 5 分半钟，发现 1 个缺陷（顶栏的剩余张数不更新），已修（见「真人走查」）。

## 容量基线

定下的数值与用法见[出图服务](service.md#容量基线)，决定见 M302、M303。这里记测量的做法与原始数字。

**做法**：`node service/scripts/capacity.mjs <阶段>`。每个阶段都先清空容器与数据卷，经平台管理员命令、开放 API 与代建推送准备租户，再经开放 API 出图。逐项用时取 worker 日志里每项一行的 `ms`；内存与 CPU 取 `docker stats`（约每秒一次）与容器 cgroup 的 `memory.peak`。原始报告在 `out/stage4/capacity/`（不进版本库）。

**测试机**：Intel Core i7-14700K（8 个性能核加 12 个能效核，28 个线程），64 GB 内存，Windows 11；Docker Desktop 29.2（WSL2，内核 6.6），给虚拟机 28 个 CPU、31 GB 内存。

### 单项画像

一个 worker，1 个 CPU、2 GB 内存（`profile`，2026-10-22 最后一次，代码已定）。用时是 worker 交付一项的用时，首项含子进程启动后第一次读字体与资源；峰值是 worker 容器的内存峰值。

| 负载 | 项数 | 首项 | 中位数 | 最慢 | 峰值 |
|---|---|---|---|---|---|
| M402 线路牌 740 × 165 mm、120 dpi（本站 1–35） | 35 | 754 ms | 1,047 ms | 1,352 ms | 319 MB |
| 价签 100 × 50 mm、300 dpi | 30 | 488 ms | 103 ms | 204 ms | 353 MB |
| 线路牌 1500 × 165 mm、338 dpi（单边 2 万像素上限，本站 1–10） | 10 | 2,267 ms | 5,272 ms | 12,584 ms | 691 MB |
| 压力细牌 2,000 项（展开上限） | 3 | 1,203 ms | 773 ms | 918 ms | 357 MB |
| 问候牌 1 亿像素（200 × 200 mm、1270 dpi，单张上限） | 3 | 3,293 ms | 2,720 ms | 2,769 ms | 1,331 MB |
| M402 草稿预览，从提交到拿到图（端到端） | 20 | 686 ms | 1,195 ms | 1,355 ms | — |

- **用时随本站序号增长**：1500 mm 宽的线路牌第 1–4 站 1.5–2.3 秒，第 10 站 12.6 秒。本机（Windows，命令行，含进程启动约 1.5 秒）第 10、20、35 站是 11.6、13.3、16.6 秒，第 10 站之后增长变慢。推断容器里第 35 站约 18 秒，这是限制之内最慢的一项。M402 的 120 dpi 也一样：第 1–4 站约 0.3 秒，第 35 站 1.3 秒。
- **给 4 个 CPU**（同一组负载另跑一次）：M402 与大图只快 2–4%（M402 1,061 → 1,022 ms，1 亿像素 2,535 → 2,492 ms），渲染时 worker 的 CPU 中位数约 101%，即一个核；价签与压力细牌快 14–31%（107 → 92 ms、743 → 512 ms），推断是垃圾回收等后台线程用上了多余的核，但它们本来就只要 0.1–0.8 秒。按 1 个 CPU 定预算，要吞吐就多起 worker。
- **单张上限的图**：1 亿像素峰值 1.31–1.33 GB，2 GB 的上限留约 0.7 GB。
- **单边上限**：1500 mm 宽时 500 dpi 是 29,528 像素，超过引擎的单边上限 20,000，入队前就失败（问题清单）；所以线路牌最大到 338 dpi。

### 千项长批次

一个 worker（`long`），M402 本站 1–35 轮转，交付 1,000 项，全部成功：

| 子进程换新 | 用时 | 每分钟 | 中位数 | 最慢 | 前 50 项 / 后 50 项中位数 | 内存（前 5% → 后 5% 时间，最大） | 换新 |
|---|---|---|---|---|---|---|---|
| 不换（100,000 项） | 944 秒 | 63.6 | 1,022 ms | 1,988 ms | 1,054 / 1,041 ms | 270 → 293 MB，310 MB | 0 次 |
| 做满 500 项 | 980 秒 | 61.2 | 1,071 ms | 2,383 ms | 1,072 / 1,075 ms | 269 → 293 MB，322 MB | 2 次 |

逐项用时前后不变；两种做法内存都只多 23–24 MB，换新不改变内存曲线，说明不是渲染子进程逐项泄漏。换新一次约 1 秒，每 500 项一次，代价不到千分之二，作为保险保留。

每个 worker 1 个 CPU（`scale`），每个 worker 200 项 M402，按每批 500 项拆开同时提交：

| worker | 项数 | 用时 | 每分钟 | 每个 worker | 中位数 | p95 | 对象存储 CPU | PostgreSQL CPU | 接口进程 CPU |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 200 | 201 秒 | 59.6 | 59.6 | 1,103 ms | 1,405 ms | 3% | 3% | 1%（峰值 160%） |
| 2 | 400 | 208 秒 | 115.2 | 57.6 | 1,129 ms | 1,426 ms | 4% | 3% | 1% |

### 长期负载

`soak --hours 3 --workers 2 --tenants 3`（M304），2026-10-22 09:42–12:44（UTC），最终代码，worker 用定下的数值（1 个 CPU、2 GB、60 秒、做满 500 项换新）：

- **负载**：3 个租户各自连续提交批次，大小在 1、10、50、200 项之间轮换，M402 与价签交替；每批结束后做一次 M402 草稿预览；每个租户注册了 webhook，投递给宿主机上的接收端。两个 worker 一直满载，队列始终有积压。

## 后续

按影响排序；都不挡本阶段的验收。

1. **整批导出的大小按项数线性增长**（容量）。每项的记录带着自己引用的字体，zip 里没有硬链接，按每项一份展开：M402 每项约 33.5 MB，千项批次的导出包约 33 GB，先写进接口进程的临时文件。这是记录自足（ADR-0019）与本地目录逐字节相同（M272）的直接后果，[出图记录说明](output-records.md)里也写了。要定的是取舍：按批次导出时在包里按哈希存一份、附还原办法（不再与本地目录逐字节相同）；或者限制整批导出的大小，大批次引导按项导出与整批图片。
2. **初始密码以 `-` 或 `_` 开头或结尾时容易复制漏**（真人走查）。第一次登录失败一次。生成初始密码时避开首尾的这两个字符。
3. **导出整批记录要等几秒，页面没有进度提示**（真人走查）。与第 1 项一起处理。
4. **用真实的 Excel 或 WPS 填写空白表再导入**（票据 13 留下的）：本次走查用的表由 openpyxl 填写，真人的表格软件仍没测。
5. **接口进程里的同步工作**：固定千项批次最长占住事件循环约 0.9 秒。切换条件见 M302。
6. **线路牌的用时随本站序号增长**：单边上限的线路牌第 1 站 2.2 秒、第 10 站 12.6 秒，原因没查（推断与已过站点的样式与排版有关）。只影响容量，不影响正确性；模板或引擎的性能优化时再看。
7. **本机模拟对象存储用的 RustFS 内存一直涨**（长期负载）：3 小时从 0.7 GiB 涨到 2.25 GiB，没看到封顶。生产用云上的对象存储或另选自建方案时，给它设内存上限并跑一次更长的负载；本机长时间运行时留意它。
8. **本机 Docker 的代理**：用户的 `~/.docker/config.json` 把 `127.0.0.1:10808` 注入容器，容器里连不上。本票用临时的 `DOCKER_CONFIG` 去掉代理，tester 镜像经 `RW_ALPINE_MIRROR` 从阿里云镜像源装 Chromium（[开发环境与接续](dev-setup.md)「已知的坑」）。
